# Known bugs, workarounds, unresolved issues

## Fixed, but easy to reintroduce

**Confidence double-calibration** (fixed, `lib/features/share/receipt_parse_pipeline.dart:79-84`) — `ocr_service_confidence` arrives from `services/ocr-api` already sigmoid-calibrated. An earlier version of `combinedConfidence` re-applied the sigmoid, crushing a legitimate 0.34 scan-quality score down to ~0.036, which forced every receipt into the review queue regardless of actual parse quality. The fix and the reasoning are documented in place — **do not re-apply calibration to `ocr_service_confidence`** when touching this code.

**Enriched place data never reached the local outbox** (fixed 2026-07-08, `lib/data/repositories/sync_worker_flutter.dart`) — `SyncWorker` invoked `enrich-transaction` but never read its response or re-fetched the row, so `place_name`/`place_google_place_id`/`place_lat`/`place_lng`/`place_confidence`/`place_status`/`merchant_normalized`/`pipeline_status` were updated in Postgres but **never written back locally**. `TransactionView.displayPlace` already correctly preferred `placeName` over `merchantRaw` — it just never had a fresh `placeName` to prefer, so the UI silently showed raw OCR text forever even after successful enrichment. Fix: re-fetch the enriched columns after invoking and write them into the local outbox via `buildEnrichmentCompanion()` (a pure, unit-tested mapper — see `test/sync_worker_test.dart`). If you touch this code path again, check that the local write-back still happens — it's easy to add a new enrichment field to Postgres and forget the local mirror again.

**`category_confidence` was never synced to Postgres** (fixed 2026-07-08, `lib/data/repositories/sync_worker_flutter.dart`) — the `transactions` upsert map omitted `category_confidence` entirely (present locally in `OutboxTransactions`, just never sent), so `enrich-transaction`'s category-biased Nearby Search (`category_confidence >= 0.5` gate, picks `restaurant`/`cafe`/etc. vs. generic place types) always saw a stale `0` and silently fell back to `DEFAULT_NEARBY_TYPES`. No error, no symptom beyond slightly-worse place matching for high-confidence category guesses — the kind of gap that's easy to reintroduce silently when adding a new field to one side of the sync (local ↔ Postgres) without the other.

## Environment/tooling gotchas (not app bugs, but will look like one)

- **`flutter test` lock errors on Windows** — Flutter's native-assets/hooks step (`sqlite3`, `jni`, `objective_c`) can leave a stale `.dart_tool/hooks_runner/*.lock` if another `dart`/`flutter` process holds it, or OneDrive delays file access. Workaround: `.\scripts\flutter_test_windows.ps1` (add `-StopDartProcesses` if locks persist). Do **not** disable native assets (`flutter config --no-enable-native-assets`) — `sqlite3`/`objective_c` need them.
- **Android `flutter run` looks hung on Gradle** — first debug builds under OneDrive can appear stuck for an hour+ downloading SDK components/compiling native deps. Move the repo off OneDrive (e.g. `C:\dev\receipt-drop`) rather than assuming it's broken.
- **OCR API port conflict** — starting `uv run ocr-api` when a previous instance (or its `uvicorn --reload` child) is still holding the port fails loudly by design (real TCP probe, not a bind test — Windows lets a second process bind an already-listening port). Use `scripts/stop_ocr_api.ps1 -Port <port>`, don't just retry.
- **Port convention mismatch**: local dev OCR API defaults to **8081** (`scripts/run_ocr_api.ps1`, root `.env.example`); the Dockerfile and `bin/process_receipts.dart --help` default to **8080**. If OCR calls fail with connection-refused, check which convention the specific script in play actually uses before assuming the service is down.
- **Friend map pins missing** — check whether `supabase/migrations/20260706000000_friend_map_pins.sql` has actually been applied to the target project (`supabase db push`) before debugging further; this migration is easy to forget when spinning up a fresh Supabase project. Also check the user's `profiles.share_map_location` (default true, but user-toggleable in Settings).
- **`GOOGLE_PLACES_API_KEY` not documented in `supabase/functions/.env.example`** — both `enrich-transaction` and `places-proxy` require it at runtime, but the example file only lists OCR-related vars. A fresh Supabase project setup will silently fail enrichment (`pipeline_status='failed_enrichment'`, no user-facing error, per the "no anxiety UI" design) until this is set manually.
- **Missing Android `INTERNET` permission** (fixed, per `[[map-flutter-map-migration]]` note) — release builds had no network at all until this was added to the main `AndroidManifest.xml`. Worth re-checking after any manifest merge/regeneration.

## Design risks flagged during documentation (not filed as bugs, but worth tracking)

- **`profiles` RLS widening**: `profiles_select_accepted_friend` (added `20260630000000_leaderboard_api.sql`) lets any authenticated user read a friend's full `profiles` row, a departure from the earlier "definer-functions-only" cross-user access stated in `20260626000002_social.sql`. Not a bug per se — a deliberate, documented tradeoff (see `docs/decisions.md`) — but worth re-auditing if `profiles` ever gains a sensitive column, since this policy would expose it to any accepted friend.
- **`merchant_aliases` is global, cross-user reference data** (`20260708000000_merchant_aliases.sql`) — deliberately shared across all users (business names aren't sensitive), unlike almost everything else in this schema. Access is function-mediated only (`lookup_merchant_alias`/`upsert_merchant_alias`, both `security definer` with `EXECUTE` explicitly revoked from `PUBLIC` before granting to `authenticated` — Postgres auto-grants new functions to `PUBLIC`, easy to forget to revoke). If you add a new function touching this table, remember the revoke-then-grant pattern or an unauthenticated `anon`-key caller could read/write the global cache directly.
- **`CategoryConfigCache` Drift table exists but nothing populates it** — the v1 spec's remote category-refresh mechanism appears unimplemented. Not currently causing incorrect behavior (bundled categories are used), but an agent asked to "why isn't the remote category config updating" should know this is dormant scaffolding, not a broken feature.
- **Impact Drops prototype has drifted from the Flutter port it inspired** — different category/theme counts, a `.glb`/three.js exception (`GlbDiorama.tsx`) not mentioned in its own `.lovable/plan.md`. If asked to "match Impact Drops' behavior exactly," verify against the *current* prototype code, not the plan doc, and expect it to no longer match the shipped Flutter behavior 1:1.
- **Duplicate import** in `lib/domain/logic/category_matcher_bundled.dart` (`import 'dart:convert';` appears twice) — harmless, trivial cleanup opportunity, not urgent.
- **Stale `build/` artifacts** reference `google_mlkit_commons`, `google_mlkit_text_recognition`, `google_maps_flutter_android` — leftovers from before the OCR/map migrations away from these. Not active dependencies (confirmed absent from `pubspec.yaml`); safe to ignore or clear with `flutter clean` if they cause confusing build errors.

## Deliberate stubs (not bugs)

- `badge_progress.dart`: `budget_buddy` and `smart_spender` badges hardcode 0 progress — the underlying budget/price-comparison features don't exist yet.
- `impact_level.dart`: RM15/RM60 thresholds for low/med/high impact are explicitly placeholder, pending real usage data.
- `get_friend_leaderboard()` ranking (streak desc, badge_count desc) is explicitly called a "placeholder pending real product sign-off" in the migration comment (`20260626000003_leaderboard.sql`).
