# Feature: AI Spending Insights

## Context

Receipt Drop's dashboard today only shows deterministic aggregates (`monthSummary`, `categoryBreakdown`, `weeklyTrend`, `topPlaces`) — the user has to interpret the numbers themselves. The product goal is to make the app feel like it *understands* the user without turning into a budgeting app: surface 1-3 short, encouraging, proactively-generated observations about their spending behavior, generated by a small swarm of specialized detectors and polished by a single AI curator, rather than one LLM ingesting the full transaction history.

This document is a product/technical specification only — it is meant to be handed to an implementing engineer or AI coding agent, who will inspect the current codebase in depth and produce their own implementation plan. No code is included below.

Three architectural decisions were confirmed with the product owner before drafting this spec (see the "Decision Logic" and "Tradeoffs" sections for the reasoning):
- **UI placement**: a compact card on the Home dashboard for the single top insight, plus a tappable detail view showing up to 3.
- **Trigger cadence**: event-triggered after sync (mirroring the existing `SyncWorker` pattern), gated by a local rate/volume guard — not a new scheduled batch job.
- **Persistence**: curated insights are persisted (new per-user table, local + cloud), not recomputed on every screen build.

**Verification pass (2026-07-28)**: every technical claim below was fact-checked directly against the current codebase. Three inaccuracies from the original draft were corrected in place: (1) `categoryConfidence` is already a first-class `OutboxTransactions`/`transactions` column, not something buried in `llm_understanding` jsonb — surfacing it on `TransactionView` is a one-line addition per mapping site, not new extraction logic; (2) the "server pushes new rows down to a client-owned local table" persistence flow is not unprecedented — `SyncWorker.run()`'s post-`enrich-transaction` read-back into `buildEnrichmentCompanion()` is a direct, reusable precedent; (3) the cited `UNDERSTAND_TIMEOUT_MS` constant does not exist — only `LLM_TIMEOUT_SECONDS = 25.0` (`services/ocr-api/ocr_api/receipt_understanding.py`) is real. Everything else — the migration-naming precedent, the absence of any cron/WorkManager/feature-flag mechanism, the OCR-cleanup cost-avoidance precedent, and `services/ocr-api`'s ownership of the LLM gateway/validation helpers — was confirmed accurate as originally written.

## Overview

AI Spending Insights is a background pipeline that turns a user's synced transactions into a small number of short, friendly, non-judgmental observations about their spending behavior — surfaced as a dismissible card on Home and a detail view behind it. It is built as an agent swarm: five specialized, deterministic (non-LLM) detectors each scan the user's local transaction data for one narrow pattern (spikes, category shifts, habits, streaks, forecasts) and emit candidate insights; a single AI Curator step then dedupes, ranks, selects the top 1-3, and rewrites them into natural language. Only the curator step calls an LLM, and only on a rate-limited cadence.

## Problem Statement

The app currently surfaces raw aggregates only (`lib/domain/logic/dashboard_aggregates.dart`) — totals, category slices, weekly trend, top places — with no synthesis or narrative. Users have to do the interpretation themselves, which undercuts the product goal of feeling like the app "understands them" and works against the stated goals of encouraging continued receipt logging and building habit awareness. There is no existing insights/notifications table or generated-content surface anywhere in the schema (confirmed against `docs/database/schema.md` and current migrations) — this is new ground, not an extension of an existing feature.

## Goals

- Detect and surface 1-3 short, specific, encouraging observations about a user's spending behavior after each meaningful sync event.
- Keep insight *detection* fully deterministic and on-device; use exactly one LLM call per generation cycle, only for ranking/dedup/rewrite.
- Let insights be revisited (detail view) and dismissed, with dismissal persisted.
- Degrade gracefully to nothing (no insight shown) rather than ever show a wrong, hallucinated, or judgmental insight.
- Work within the existing local-first, cloud-enriched architecture and its established RLS/Edge-Function/cost-control conventions.

## Non-Goals

- No cross-user comparison of spending amounts (explicit product constraint) — the Habit/Streak agents may reference the user's own gamification data (badges, streak) but never a friend's numbers.
- No traditional budgeting features (budgets, limits, alerts framed as warnings) — insights must read as observations, not judgments.
- No new insight agents beyond the five specified here (Spending Spike, Category Shift, Habit, Streak/Motivation, Forecast) — additional agents are future work (see below).
- No scheduled/cron-style batch generation — out of scope for v1 given no such infrastructure exists in this codebase today (confirmed: no WorkManager/BGTaskScheduler/cron pattern anywhere).
- No changes to the capture/OCR/sync critical path — insight generation must be additive and non-blocking to `SyncWorker`, never able to delay or fail a receipt sync.
- No on-device LLM — all LLM calls happen server-side, consistent with the existing architecture (`services/ocr-api` is the only current LLM caller).

## Proposed Solution

Detection runs entirely on-device: five new pure Dart functions, written alongside the existing aggregates in `lib/domain/logic/dashboard_aggregates.dart`'s style (reusing `monthSummary`, `weeklyTrend`, `topPlaces`, `currentDailyStreak`, `badgeProgress` as building blocks where possible), each scan the user's local `List<TransactionView>` and emit zero or more small structured "insight candidates" — no LLM involved at this stage, consistent with this codebase's repeated heuristic-over-ML precedent (`docs/system/decisions.md` — e.g. the adaptive-OCR and receipt-layout-analyzer entries both explicitly reject an ML/LLM layer in favor of hand-inspectable heuristics).

Generation is triggered the same way sync already is: fired (`unawaited`, non-blocking) from the success path of `SyncWorker.run` in `lib/data/repositories/sync_worker_flutter.dart`, but gated by a cheap local guard (time-since-last-generation + minimum new-data threshold) so it doesn't fire on every single receipt. When the guard passes, the small candidate pool (not raw transactions, not line items, not OCR text) is sent to a new server-side curator step — a new Edge Function analogous to `enrich-transaction`, backed by an LLM call — which dedupes, ranks, selects the top 1-3, and rewrites them into user-facing copy. The curated result is written to a new per-user Postgres table (owner-only RLS, matching `user_category_preferences`/`user_field_corrections`) and mirrored into a new local Drift table for offline display, dismiss-state, and the detail view.

## User Experience

**First-time / sparse-data user**: no candidates clear the data-sufficiency bar for any agent (see Edge Cases) → no card appears at all. No empty-state nagging, no "not enough data" messaging — the feature is simply invisible until it has something real to say, consistent with "avoid feeling like a traditional budgeting app."

**Returning user, normal flow**: after a receipt syncs and the local guard passes, generation runs in the background. Next time Home is opened (or the next `StreamBuilder` emission if already open), a compact single-line insight card appears above/near the existing streak/avatar area, showing the single top-ranked insight with a lightweight icon keyed to its type. Tapping it opens a small detail view listing up to 3 curated insights for the current cycle. Each insight in the detail view can be dismissed individually; dismissing removes it from both views immediately (optimistic local write) and is persisted so it won't reappear.

**Failure / degraded states**:
- Curator LLM call times out or errors: the cycle produces no new insights; previously-persisted, non-dismissed insights (if any) continue to show. No error is surfaced to the user — this is a silent-degrade, not a blocking failure (explicitly not the "no-fallback" pattern `enrich-transaction` currently uses, which decisions.md flags as testing-phase-only and unfit to copy for a production-facing feature).
- Curator returns malformed/unschema'd/hallucinated content: rejected client- or server-side before persistence; treated the same as a timeout (no new insight that cycle).
- Offline: detection still runs on-device (no connectivity needed); the curator call is deferred and retried on next successful sync, same retry semantics as `SyncWorker`.

## System Impact

- **Client application**: new pure-function detectors in `lib/domain/logic/`; a new small repository/worker class (parallel to `SyncWorker`) to own the local guard, local persistence, and curator-call trigger; a new Home card widget and a new detail-view screen registered with `go_router`; extension of `TransactionView`/its four mapping sites only if a specific agent needs a field not currently exposed.
- **Backend services**: one new Edge Function (curator orchestration, modeled on `enrich-transaction`) and a new or extended LLM-calling endpoint — most likely an addition to `services/ocr-api` (it already owns the LLM gateway client, timeout/token-cap config, and structured-output validation helpers) rather than a new sibling service, though this needs confirming against `services/ocr-api`'s internal structure (flagged as open in Implementation Guidance).
- **Database/storage**: one new Postgres table for curated insights (owner-only RLS, `security invoker`, per-user) plus its Drift mirror table and a `schemaVersion` bump/`onUpgrade` migration.
- **AI/ML pipeline**: exactly one new LLM call site (the curator), rate-limited by the generation guard; zero new LLM calls in the five detector agents.
- **Infrastructure**: none beyond the above — no new scheduler/cron infrastructure (explicit non-goal).
- **External integrations**: none new; reuses the existing LLM gateway already wired into `services/ocr-api`.

## Technical Design

**Detection layer (on-device, deterministic).** Five candidate-generating functions, one per agent, operating on the user's already-synced `List<TransactionView>` (the same reactive stream `dashboard_screen.dart` already consumes via `AppServices.transactions.watchAll()`). Each function is a pure, synchronous, unit-testable transform — no I/O, no LLM — returning zero or more small structured candidates (a type tag, the concrete numeric/categorical facts that justify it, e.g. "which category," "what percentage," "how many occurrences," and a locally-computed novelty/severity score used later for ranking). This mirrors the existing `dashboard_aggregates.dart` design exactly: given the closed feature_graph note that this file is "safe to extend without touching capture/sync," it's the natural home for these functions, or a sibling file in the same directory if kept separately for clarity.

Several agents need calculations that don't exist yet as aggregates and will need new pure functions following the same style: a per-day-of-week historical baseline (Spending Spike Agent's "2.5x your usual Saturday" needs a rolling average per weekday, not currently computed anywhere); a week-over-week category comparison (`categoryBreakdown` is month-scoped only); a short-window place-visit-frequency grouping (`topPlaces` is month-scoped top-5, not "same place N times in 7 days"); and a pace/forecast projection combining `monthSummary`'s current-month total with elapsed-days extrapolation compared against the prior month's final total. The Streak/Motivation Agent needs no new calculation — it directly reuses `currentDailyStreak()` and `badgeProgress()` from `lib/domain/logic/badge_progress.dart`.

**Trigger and local guard.** A new worker class, structurally parallel to `SyncWorker` (`lib/data/repositories/sync_worker_flutter.dart`): fired `unawaited` from `SyncWorker.run`'s success path (after a transaction reaches `synced`), it first checks a cheap local guard — time elapsed since the last generation cycle, and/or a minimum count of newly-synced transactions since then — stored as local state (e.g. a single row/preference, not per-transaction). If the guard fails, it no-ops immediately. If it passes, it runs all five detector functions over the current in-memory transaction list, assembles the candidate pool, and calls the curator Edge Function.

**Curation layer (server-side, one LLM call).** A new Edge Function, modeled directly on `enrich-transaction`'s BFF pattern (thin orchestration, per-user JWT-scoped invocation, secrets never client-side), receives only the small candidate pool — structured facts, never raw transactions, line items, merchant names beyond what a candidate already references, or OCR text. It forwards to an LLM-calling backend (most likely `services/ocr-api`, reusing its existing gateway client and timeout/token-cap config) with a prompt constrained to: dedupe, rank by importance/novelty/usefulness, select the top 1-3, and rewrite each into one friendly sentence — never introducing a fact, number, or category not present in the candidate it's rewriting. The response is validated against a closed schema before persistence, following the same strict-validation convention as `parse_receipt_understanding()` in `services/ocr-api` (coerce/validate every field, whitelist the insight "type" tag against the five known agent types, reject anything that doesn't parse cleanly — degrade to "no new insight" rather than persist something unvalidated).

**Persistence and sync-down.** Curated insights are written to a new Postgres table (per-user, owner-only RLS/`security invoker`, matching `user_field_corrections`' role as "per-user generated/logged content") by the Edge Function itself (it holds the user's JWT context). The client mirrors this into a new local Drift table. This is not as uncharted as it first looks: `SyncWorker.run()` already does a version of "server computes, client pulls the result down into its local mirror" today — after invoking `enrich-transaction`, it performs a follow-up `select()` read-back on `transactions` and writes the result into the local outbox via `buildEnrichmentCompanion()` (`lib/data/repositories/sync_worker_flutter.dart`, the `refreshed`/`buildEnrichmentCompanion` block immediately after the `functions.invoke('enrich-transaction', ...)` call). That existing two-step shape (invoke, then read back and patch locally) is the closest and most directly reusable precedent for the curator flow, and should be followed rather than inventing a new mechanism. Two viable variants, both consistent with that precedent: (a) the curator Edge Function's HTTP response body includes the newly-created insight rows directly, and the client writes them locally off that same response (saves a round-trip vs. today's pattern); or (b) mirror today's shape exactly — invoke the curator, then a follow-up `select()` on the new insights table. Either is an incremental extension of an existing pattern, not new architecture; (a) is preferred for lower latency/one fewer network call, but (b) is the more literal precedent match if the implementing engineer prefers consistency over the small latency win.

## Decision Logic

- When a transaction reaches `synced` status in `SyncWorker.run`: after existing logic completes, check the local insight-generation guard.
- If the guard fails (too little time elapsed, or too few new synced transactions since the last cycle): do nothing, no LLM call, no candidate computation.
- If the guard passes: run all five detector functions over the full current `List<TransactionView>`, filtered to `includeInCharts == true` (excluding `failed_enrichment` rows with no amount and any row currently under `needs_review`), matching the same inclusion rule the existing chart aggregates already use.
- Each detector independently decides whether it has enough data and a strong-enough signal to emit a candidate; if not, it emits nothing — there is no forced minimum output per agent.
- If the combined candidate pool is empty after all five agents run: skip the curator call entirely (no LLM cost for a cycle with nothing to say).
- If candidates exist: call the curator with the full pool. The curator must select at most 3, must not fabricate content outside the given candidates, and must return a type tag from the closed five-agent vocabulary for each selected insight.
- If the curator call fails, times out, or returns content that fails schema/whitelist validation: persist nothing new this cycle; previously-persisted, non-dismissed insights remain visible until dismissed or naturally superseded by a future successful cycle.
- On successful curation: persist the new insights (server-side write), return them in the same response, and have the client mirror them locally immediately.
- A user dismissing an insight: write the dismissed state locally first (optimistic, immediate UI removal), then sync it up on the existing outbox-style fire-and-forget pattern; a dismissed insight is never re-shown even if a later cycle's candidate pool contains the same underlying fact (dedup against dismissed history, not just within a single cycle).
- Low-confidence transactions: any transaction whose amount/category confidence is below whatever threshold the eventual implementation deems reliable should be excluded from detector input the same way `includeInCharts` already excludes unreliable rows — exact thresholds are not yet determined and need product/engineering input. Note this is a smaller lift than it might sound: `categoryConfidence` is already a first-class column (`OutboxTransactions.categoryConfidence` / Postgres `transactions.category_confidence`), populated by the parse pipeline and flowing through `ingest_receipt_request.dart` today — it is simply not yet exposed on the narrow `TransactionView` read-model. Adding it is a one-line addition at each of the four mapping sites (see Implementation Guidance), not new jsonb-extraction logic.

## Edge Cases

- **New user, zero or near-zero transaction history**: every detector requiring a historical baseline (Spike, Category Shift, Forecast) has no baseline to compare against and must emit nothing rather than a false/trivial candidate; only Streak (day-1 case) could theoretically emit something, and even that should require a sensible minimum (e.g. not fire on day 1).
- **Sparse data (a handful of transactions over months)**: same principle — each detector's own data-sufficiency check (not a global gate) determines whether it emits; a sparse user may get zero insights indefinitely, which is the correct behavior, not a bug.
- **Incorrect/low-confidence OCR data**: excluded at the detector-input filtering stage (see Decision Logic); an insight should never be generated off a transaction whose amount or category is unreliable.
- **Duplicate insights across cycles**: curator dedupes within a single candidate pool; the generation worker additionally must not resurface an insight whose underlying fact was already shown (and not dismissed) in the immediately preceding cycle, to avoid the card feeling repetitive/spammy.
- **Curator LLM timeout or malformed response**: treated as "no new insights this cycle," never as an app-visible error (see Decision Logic and UX).
- **Concurrent/re-entrant generation triggers** (e.g. two receipts sync in quick succession): guard via a status flag on the local generation state, the same way `SyncWorker` checks for `'syncing'` before re-entering, so two overlapping trigger events don't both fire the curator call.
- **Offline curator call**: detection still runs (on-device), but the curator call itself needs connectivity; if offline, defer and retry on next successful sync using the same retry semantics `SyncWorker` already has (bounded retry count, eventual `'stuck'`-equivalent state) rather than inventing new retry logic.
- **User dismisses an insight, then the same fact would otherwise reappear next cycle**: must stay suppressed (see dedup-against-dismissed-history above), not just deduped within a cycle.

## Performance Considerations

- Detection is pure in-memory Dart over a list already held for existing dashboard aggregates — same cost class as `monthSummary`/`categoryBreakdown`, negligible added latency, safe to run synchronously off the main sync callback.
- The curator LLM call is the only network/latency-sensitive step; it must have a strict timeout, following the existing precedent of `LLM_TIMEOUT_SECONDS = 25.0` in `services/ocr-api/ocr_api/receipt_understanding.py` (the only such timeout constant confirmed in this codebase — there is no separate `UNDERSTAND_TIMEOUT_MS`), and a small, bounded payload — a handful of short structured candidates, never full transaction/line-item/OCR data — keeping token cost low and predictable per call.
- Cost is primarily controlled by generation *frequency*, not per-call size: the local rate/volume guard is the main lever, directly answering the stated "minimize unnecessary LLM calls" constraint. Exact guard thresholds (e.g. "once per day" vs "every 5 new receipts") are not yet determined and should be tuned once real usage data exists — this mirrors the project's own documented precedent of shipping the simple version first and deferring cost-optimization tuning (`pending-tasks.md`'s merchant-intelligence entry).
- No added cost when a cycle produces zero candidates — the curator is skipped entirely in that case (see Decision Logic), so idle/sparse users never generate LLM spend.

## Security Considerations

- The new insights table must use owner-only RLS (`user_id = auth.uid()`, `security invoker`), matching `user_category_preferences`/`user_field_corrections` — not the locked-down zero-RLS/service-role pattern reserved for shared caches like `merchant_aliases`, since this is per-user generated content, not a cross-user resource.
- The curator Edge Function must be invoked per-user, scoped to that user's own JWT, exactly like `enrich-transaction` today — it must never batch or see data across users, both for RLS correctness and because "never compare users' spending" is an explicit product constraint, not just a UX preference.
- Only the small candidate pool (aggregated facts) is ever sent to the LLM — no raw OCR text, no line items, no merchant/location data beyond what a specific candidate already legitimately references. This is a privacy-by-minimization design choice, not just a cost one.
- The curator's returned insight "type" tag must be validated against the closed five-agent vocabulary before being trusted by any client-side rendering/icon logic, mirroring the existing whitelist-validation pattern used for `vendor_category`/`google_place_types` — an unvalidated free-form type string reaching the client is both a hallucination risk and a potential rendering-logic footgun.

## Tradeoffs

- **On-device deterministic detection vs. sending full transaction history to a cloud LLM for open-ended analysis**: rejected the latter. It would violate the local-first architecture, repeat a cost mistake this project already explicitly avoided once (`docs/system/decisions.md`'s 2026-07-23 "LLM-based OCR cleanup" entry explicitly rejects "a second dedicated LLM call for cleanup only" on latency/cost grounds, reusing the existing single call instead), contradict the repeated "heuristic-over-ML" precedent documented for the adaptive-OCR and receipt-layout-analyzer work, and unnecessarily expose more raw data to a network call than the feature needs.
- **Event-triggered-after-sync vs. a scheduled nightly batch job**: rejected the scheduled option for v1. No cron/WorkManager/BGTaskScheduler pattern exists anywhere in this codebase today, so it would be new infrastructure for a feature that doesn't need clock-precision — event-triggered-with-a-guard achieves the same cost control by reusing the exact shape of the existing `SyncWorker` trigger, at far lower implementation risk.
- **Persisted insights vs. ephemeral recompute-on-build**: chosen persisted, despite the extra table/migration/mirroring work, because (a) the confirmed UX (Home card + detail view) implies insights should be revisitable, not just glanced at once, (b) dismiss-state requires somewhere durable to live, and (c) recomputing on every screen build would mean re-running the curator's LLM call on every app open unless a separate in-memory cache were invented anyway — persistence is the simpler mechanism, not the more complex one, once dismiss/revisit is a requirement.

## Implementation Guidance

Suggested order of work:
1. Only extend `TransactionView`/its four mapping call sites (`lib/domain/models/transaction_view.dart`, both `transaction_repository_native.dart`/`_web.dart` `_mapRow` implementations, and any `copyWith`) if a specific detector genuinely needs a field not already exposed (e.g. `categoryConfidence` for confidence-gating the Category Shift agent) — treat this as a last resort, since it's a wider blast radius than it looks (four spots, not one).
2. Write the five detector functions plus any new supporting calculations (per-weekday baseline, week-over-week category delta, short-window visit-frequency grouping, pace/forecast projection) alongside `lib/domain/logic/dashboard_aggregates.dart`, reusing `monthSummary`, `weeklyTrend`, `topPlaces`, `currentDailyStreak`, `badgeProgress` as building blocks. These are the most independently testable and lowest-risk part of the feature — start here.
3. Design and build the local guard + generation-trigger worker, inspecting `lib/data/repositories/sync_worker_flutter.dart` closely for the fire-`unawaited`-from-a-write-success-path pattern, the status-flag re-entrancy guard, and the per-substep try/catch isolation convention — the new worker should follow the same shape, not invent a new one.
4. Add the Postgres migration for the new insights table, following the newest 2-3 files in `supabase/migrations/` for current conventions; `20260723010000_user_field_corrections.sql` is the closest existing precedent for a per-user generated/logged-content table and its RLS shape.
5. Add the Drift mirror table, bump `schemaVersion`, and write the `onUpgrade` migration step.
6. Add the curator Edge Function (new, modeled on `enrich-transaction`) and its backend LLM call. Before committing to where the LLM call itself lives, inspect `services/ocr-api`'s internal structure to judge whether extending it (reusing its existing gateway client, token/timeout config, and structured-output validators) is cleaner than standing up a new sibling service — this spec cannot resolve that without seeing `ocr-api`'s current boundaries, so treat it as an open call for whoever implements this.
7. Wire the trigger into `SyncWorker.run`'s success path.
8. Build the Home card widget (`lib/features/home/`) and the new detail-view screen, registering its route with the existing `go_router` config, following `home_screen.dart`'s existing `StreamBuilder`-over-Drift pattern — there is no state-management library in this project (no riverpod/provider/bloc), so the dismiss interaction needs to fit that raw-`StreamBuilder` pattern rather than introducing a new one ad hoc.

Risks to flag going in: (a) the server-writes-then-client-mirrors-locally flow has a directly reusable precedent — `SyncWorker.run()`'s post-`enrich-transaction`-invoke read-back into `buildEnrichmentCompanion()` (`lib/data/repositories/sync_worker_flutter.dart`) — inspect that block closely before designing the curator's persistence step from scratch; (b) `TransactionView` is a deliberately narrow read-model touched at four separate mapping sites, so any field extension has a wider footprint than it first appears; (c) exact guard thresholds and confidence-gating cutoffs are explicitly left undetermined in this spec and need a product/engineering call once real usage data exists, not a guessed constant baked in at implementation time.

## Testing Strategy

- Fixture-based unit tests for each of the five detector functions in isolation — feed synthetic `List<TransactionView>` and assert candidate-emitted/not-emitted at boundary conditions (e.g. exactly at a spike threshold, exactly zero prior-week data, exactly the minimum visit count), following the existing fixture style in `test/transaction_repository_test.dart`.
- Validation tests for the curator response handling: malformed JSON, an unknown/off-whitelist type tag, and a response referencing facts not present in the candidate pool must all be rejected, never persisted.
- A test for the local generation guard: verify it does not double-fire within its window, and does fire once its threshold (time or new-transaction count) is met.
- A widget test for the Home card and detail view, covering the dismiss interaction and its immediate optimistic removal, following the existing widget-test pattern visible in `test/spend_map_screen_test.dart`.
- No performance/load test is warranted pre-launch given the low call volume this feature is designed to produce (a handful of LLM calls per user per day at most) — defer to real usage monitoring instead, consistent with this project's "ship simple, tune later" precedent.

## Rollout Plan

Ship the deterministic detector layer and local persistence first, with the curator LLM call either disabled or stubbed to a simple non-LLM templated fallback string (e.g. "your top category this week was X"), as an internal soft-launch — this validates the detection logic, the new table/RLS, and the UI end-to-end without any LLM cost or hallucination risk. Enable the real curator call once that's validated. Confirmed: this project has no feature-flag/remote-config mechanism today (`lib/core/config` contains only `env.dart` and `auth_redirect.dart`, neither of which is a flag system) — building one is out of scope for this feature, so the single `SyncWorker`-trigger call site doubles as the kill switch instead: disabling it there stops all new generation immediately, and any already-persisted insight rows remain harmless and inert if the UI surface is hidden client-side. No backward-compatibility concerns exist since this is entirely new data with no prior consumers.
