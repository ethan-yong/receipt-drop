# Feature: Token-Level OCR Confidence Tracking and Confidence-Aware Extraction

## Overview

Extend the OCR/parsing pipeline to preserve and propagate fine-grained (word- and line-level, region-aware) OCR confidence instead of collapsing it into a single per-receipt mean before parsing decisions are made. The existing heuristic extractors (`rm_amount_parser.dart`, `merchant_extractor.dart`, `receipt_line_item_extractor.dart`) already do multi-candidate scoring and cross-field reconciliation — this feature feeds them a reliability signal they currently don't have, so a candidate's OCR trustworthiness becomes part of how it's scored, not just its regex/keyword/geometry fit.

## Problem Statement

`services/ocr-api/ocr_api/ocr_engine.py`'s `_run_tesseract` already iterates Tesseract's per-word confidence values internally, but reduces them to a single per-line mean (further reduced to a single per-request mean) before anything is returned — word-level detail is discarded in the same pass it's computed, never materialized in any structure, internal or external. Three concrete consequences:

1. **A single bad word can hide inside a good line average**, and a single bad line average can hide inside a good receipt average — `combinedConfidence` (`lib/features/share/receipt_parse_pipeline.dart`) can be high while the actual digits or letters composing a critical field are individually unreliable.
2. **`_normalize_ocr_amounts`'s digit-confusion correction (Z/z/O/l/I → 2/2/0/1/1) is applied blind to confidence** — it unconditionally trusts every regex match in the already-joined line text, with no way to flag "this digit was a guess" to anything downstream.
3. **The extractors have no OCR-reliability input at all today.** `rm_amount_parser.dart` and `receipt_line_item_extractor.dart` score candidates purely from regex-tier/keyword/position/cross-check heuristics; `merchant_extractor.dart`'s only OCR-derived signal is line `heightRatio` (geometry, not confidence). None of the three can currently distinguish "this candidate came from text Tesseract was confident about" from "this candidate came from a guess."

## Goals

- Preserve per-word confidence (text, calibrated confidence, digit-correction flag, horizontal position) through the OCR pipeline instead of discarding it after line-level reduction.
- Expose line-level confidence to the client for the first time (`OcrLine` currently carries geometry only, no confidence field at all) and word-level confidence selectively, without duplicating or conflicting with the existing `ocrConfidence` (extraction) / `ocrServiceConfidence` (scan quality) distinction.
- Feed OCR-reliability signal into the three existing extractors' scoring functions as an additive input, not a replacement of their existing regex/keyword/cross-check logic.
- Extend the existing item-sum↔total reconciliation and merchant multi-candidate ranking with confidence-aware "reject or surface alternatives" behavior for the three critical fields (amount, subtotal, merchant).
- Give the main LLM understanding prompt (not just the opt-in cleanup prompt) access to confidence information, reusing the existing tagging pattern.
- Surface per-field (not just receipt-level) low-confidence indicators in `ReceiptConfirmSheet`, using data that's mostly already collected but not yet shown.

## Non-Goals

- **No character-level confidence tracking.** Tesseract's word-level API (`image_to_data`) is what the pipeline already calls; character-level would require a different call (`image_to_boxes` or box-level TSV output) the codebase doesn't use today. Digit-confusion correction is already word-scoped (`_normalize_ocr_amounts` operates on numeric spans, not individual characters), so word-level granularity already lets downstream logic flag exactly the suspect token. Revisit only if word-level proves insufficient — not assumed here.
- **No redesign of the existing receipt-level confidence blend** (`combinedExtractionWeight = 0.6`, `combinedScanWeight = 0.4`, `combinedScanCeilingMargin = 0.25` in `receipt_parse_pipeline.dart`). This feature improves the `ocrConfidence` value that *feeds* that blend by making extractors confidence-aware; it does not change the blend formula or its weights, which were already deliberately tuned. Changing them is out of scope.
- **No blocking-save / forced-confirmation UI.** CLAUDE.md's local-first architecture ("saves it instantly to a local offline outbox") is a hard constraint — every capture must still write to Drift and return immediately regardless of confidence. This feature can make low-confidence fields more visible and offer the existing "Save for later" review-queue path more precisely, but must never gate the initial save on user confirmation.
- **No changes to the `pipeline_status`/`needs_review` state machine itself** (its columns, sync semantics, or Drift schema). This feature changes the *signals* feeding the existing `needsAmount`/`lowConfidence` flags that route into that machine, not the machine.
- **No image-overlay/bounding-box highlighting UI.** Per-word horizontal position (`left_ratio`/`width_ratio`) is captured server-side because it's free (already computed in the same Tesseract pass) and future-proofs, but no UI in this codebase today overlays bounding boxes on the receipt image — visually highlighting a specific suspect word in-image is out of scope for v1.
- **No new analytics/event-tracking infrastructure.** "User correction frequency" (Testing Strategy) needs a way to detect post-save edits; if no such tracking exists today, adding it is a prerequisite this feature assumes but does not build (flagged explicitly, not assumed present).
- **No change to the existing LLM-overrides-heuristics precedence rule.** `receipt_parse_pipeline.dart` already lets `understanding` (LLM) fields take precedence over heuristic extraction when present; this feature enriches what the LLM is given (confidence tags) and what the heuristics compute (confidence-aware scores), but doesn't change which one wins when both are present.

## Proposed Solution

Retain per-word `(text, confidence, digit_corrected, left_ratio, width_ratio)` tuples inside `_run_tesseract`'s existing single pass over Tesseract's word arrays, instead of discarding them immediately after the per-line mean is computed. Calibrate each word's confidence with the same existing sigmoid function already used for line/request means (`_calibrate_confidence` — no new calibration logic needed, just additional call sites), computed independently of the (unchanged) line-mean calibration so today's line/request confidence numbers — and every threshold tuned against them — don't silently shift.

Extend the public `OcrLine` model with the line confidence it currently lacks entirely, plus an optional per-word list populated selectively: full word-level detail is only attached to lines whose own confidence falls below a threshold, keeping payload growth near zero for well-scanned receipts (most lines) while giving full detail exactly where extraction logic needs it (poorly-scanned lines).

On the client, add an OCR-confidence-derived scoring term to each of the three existing extractors' already-multi-signal scoring functions, additively alongside their existing regex/keyword/position/cross-check terms — not a rewrite. Extend the existing item-sum↔total reconciliation loop and merchant top-5 ranking to also flag "suspicious" results (matched digits/text individually low-confidence, no cross-check corroboration, plausible alternative exists) and, in that case, surface the runner-up alongside the winner instead of silently committing — reusing `merchant_extractor.dart`'s existing multi-candidate return shape, and extending `rm_amount_parser.dart` to return its full ranked candidate list (already computed internally) instead of just the winner, mirroring the pattern that already exists for merchant.

## User Experience

No new screen or flow — this extends the existing post-OCR confirm step (`ReceiptConfirmSheet`).

- **Golden path (high confidence throughout):** unchanged. User sees the parsed amount/merchant/items pre-filled, taps save. No new UI appears.
- **Single low-confidence field:** today, a single generic banner appears only when the *combined receipt-level* score is low or the amount is missing. New: the specific field (amount input, merchant name, or an individual line-item row) gets its own subtle low-confidence indicator (e.g. a warning-tinted border/icon), so the user's attention goes to the actual problem field instead of a generic "double-check this" message pointing at nothing specific.
- **Ambiguous critical field (two plausible candidates, neither clearly better):** for merchant, a small "not this?" affordance lets the user pick the runner-up from the already-computed top-5 candidates (today only the top-1 is used via `extractMerchant()`) instead of silently committing to #1. For amount, the same pattern is added — today `parseRmAmountFromOcr` only returns its winning candidate; this extends it to return the ranked list so an equivalent "did you mean RM X?" affordance is possible.
- **Suspicious total (matches the regex, but individually low-confidence and not corroborated):** downgrades into the *existing* "Save for later" review-queue path (unchanged mechanism) rather than a new blocking state — consistent with the no-blocking-save Non-Goal.
- **Error handling:** if word-level data is missing/malformed (e.g. an older cached response, or the server has the feature flag off), all confidence-aware logic falls back to today's behavior exactly — this must be a strict superset, never a required field, so absence degrades gracefully rather than erroring.
- **Feedback mechanism:** per-field indicators replace the single generic banner's imprecision, but the overall interaction model (inline tap-to-edit, item exclusion with undo) is unchanged — this feature sharpens *where* attention is drawn, not the editing mechanics themselves.

## System Impact

- **Backend services:** `services/ocr-api` — `_run_tesseract`/`ocr_engine.py` retains and calibrates per-word data instead of discarding it; `_normalize_ocr_amounts` gains awareness of which digits it corrected (a new signal, not a new correction rule); `models.py` gains a new internal word-level dataclass and public `OcrWord`/`OcrLine.confidence`/`OcrLine.words` fields; `receipt_understanding.py`'s main (non-cleanup) prompt-construction path gains the same per-line confidence tagging the cleanup prompt already has.
- **Client application:** `lib/domain/models/ocr_line.dart` gains a `confidence` field and an optional `words` list (new `OcrWord` model, mirroring the Python addition); `lib/domain/logic/rm_amount_parser.dart`, `merchant_extractor.dart`, `receipt_line_item_extractor.dart` each gain an additive OCR-confidence scoring term; `lib/features/share/receipt_parse_pipeline.dart` gains a `merchantConfidence` top-level getter (mirroring the existing `ocrConfidence` pattern) and surfaces ranked alternative candidates for amount (new) alongside the existing ones for merchant; `lib/features/share/receipt_confirm_sheet.dart` gains per-field indicators and an alternate-candidate picker for ambiguous fields.
- **Database/storage:** None. No schema change — `pipeline_status` and its Drift mirror are untouched (Non-Goal).
- **AI/ML pipeline:** No new model. The existing LLM understanding call gains richer prompt input (confidence tags on the main extraction prompt, reusing the cleanup prompt's existing tagging code path) but is still exactly one call per receipt, unchanged in count/timing.
- **Infrastructure:** None.

## Technical Design

**Word-level retention in `_run_tesseract`.** The existing single pass over `pytesseract.image_to_data()`'s parallel arrays already visits every word once to build the per-line accumulator dicts (`lines`, `heights`, `lefts`, `tops`, `rights`, `line_confidences`, keyed by `(block_num, par_num, line_num)`). This feature adds one more accumulator, keyed the same way, holding each word's `(text, raw_conf, left_ratio, width_ratio)` in the order encountered. After the existing per-line reduction produces `OcrLineResult`, a new step maps each accumulated word through `_calibrate_confidence(raw_conf / 100.0)` (same pure function, new call sites, applied to the word's own raw confidence rather than a line mean) and attaches the resulting list as a new field on `OcrLineResult`. **The existing line-level and request-level mean/calibration math is untouched** — it still computes calibrate(mean(raw)), not mean(calibrate(raw)); these are numerically different due to the sigmoid's nonlinearity, and changing which one existing thresholds (the 0.4 retry trigger, the 0.5 client low-confidence threshold, the blend's `+0.25` ceiling) were tuned against is explicitly out of scope for this feature.

**Digit-correction flagging in `_normalize_ocr_amounts`.** Today this function receives the already-joined line text and blindly substitutes confusable characters inside any `RM<amount>`-shaped regex match. This feature changes its input to operate per-word (now that word boundaries survive past the line-join step) so that when a substitution is applied to a given word, that word's carried-forward record gets a `digit_corrected: true` flag — a new reliability signal independent of (and often more informative than) Tesseract's own confidence number for that word, since confusable-character correction is inherently a guess regardless of how "confident" Tesseract was in the wrong character.

**Selective enrichment for the public `OcrLine` contract.** `OcrLine` currently has no confidence field at all (deliberately — its docstring in `ocr_engine.py` states confidence wasn't surfaced because "nothing downstream needs it"; this feature reverses that decision because something now does). Every `OcrLine` gets its line-level calibrated confidence (cheap, already computed today, just not returned). The optional `words` list is attached **only when the line's own confidence is below a threshold** (provisional default, not yet tuned — see Decision Logic) — this bounds response payload growth to the lines that actually need scrutiny, while well-scanned receipts (the common case) see near-zero payload change.

**Main LLM prompt gains confidence tags.** `receipt_understanding.py`'s cleanup-only prompt already renders `[i] (confidence 0.87) TEXT` per line via `_build_cleanup_line_block`. This feature reuses that exact rendering for the **main** (non-cleanup) understanding prompt as well — today that prompt gets plain `ocr_text` with zero confidence information, even when `OcrLineResult` data (and thus per-line confidence) is available. Word-level tags are **not** added to the LLM prompt by default — only for lines whose confidence is already below the enrichment threshold, using compact inline word-confidence annotation for just those lines, keeping prompt size bounded while giving the LLM detail exactly where the heuristic layer also needed it.

**Extractor scoring extensions (additive, not rewrites).** Each of the three Dart extractors already computes a multi-term score per candidate:
- `rm_amount_parser.dart`: base pattern-match score, then position/footer/keyword/discount boosts and penalties, then `_crossCheckAdjust` against line-item reconciliation, then cluster-consensus boost. This feature adds one more term: an OCR-confidence-derived adjustment based on the confidence (and `digit_corrected` flag) of the specific line/word(s) the matched amount came from — a corrected or low-confidence digit sequence gets a penalty analogous to the existing `_largestItemMimicryPenalty`, not a hard rejection, so a corroborated-but-low-confidence total can still win.
- `merchant_extractor.dart`: each of its five passes (header/keyword/largeText/position/fallback) already assigns a fixed or geometry-derived confidence; this feature blends in the underlying line's OCR confidence as an additional multiplicative or additive factor, so a large-font line that's also OCR-confident outranks a large-font line that Tesseract struggled with.
- `receipt_line_item_extractor.dart`: `_lineConfidence()`'s existing penalties (short/long name, out-of-range price, wrong zone) gain one more penalty term sourced from the matched name/price tokens' OCR confidence, feeding into the same aggregate confidence that already drives `reconcileWithTotal()`.

**Critical-field protection extends existing infrastructure, doesn't replace it.** The item-sum↔total bidirectional reconciliation (`reconcileWithTotal` / `_crossCheckAdjust`) and merchant's top-5 ranking are already the redundancy/cross-check mechanisms this codebase has; this feature adds a "suspicious result" classification on top: a result is suspicious when its underlying OCR confidence is low **and** cross-check corroboration is absent **and** a meaningfully different alternative candidate exists. Suspicious results route into the existing "Save for later" path and, in the UI, expose the alternative rather than silently discarding it.

## Decision Logic

- When retaining word data in `_run_tesseract`, calibrate each word's confidence independently via the existing `_calibrate_confidence` function; never reuse or overwrite the line-mean calibration already computed for that line.
- When `_normalize_ocr_amounts` substitutes a confusable character in a word, mark that word `digit_corrected: true` regardless of Tesseract's own confidence for that character — a correction is evidence of uncertainty even when the raw confidence number looks fine.
- When constructing the public `OcrLine` for a given line, always include its calibrated line confidence. Include the per-word `words` list only if that line's confidence is below the enrichment threshold (provisional default 0.7, matching the codebase's existing `lowOcrConfidenceThreshold` order of magnitude — not yet validated, needs tuning via dataset evaluation before being treated as final).
- When building the main (non-cleanup) LLM understanding prompt, tag every line with its calibrated confidence using the existing cleanup-prompt tagging format. Additionally inline word-level confidence tags only for lines below the same enrichment threshold used for the client response, so prompt size scales with the number of uncertain lines, not receipt length.
- When `rm_amount_parser.dart` scores a candidate, apply an OCR-confidence penalty proportional to how low the matched line/word's confidence is, and an additional penalty if any digit in the match was `digit_corrected`. Do not let this penalty alone override a strong cross-check corroboration boost (subtotal agreement) — corroborated-but-uncertain should still be able to win over uncorroborated-but-confident, since corroboration is stronger evidence than raw OCR confidence.
- When the top-scoring amount candidate's underlying OCR confidence is below a hard floor (provisional, not yet determined — needs dataset input) **and** no cross-check corroboration applies **and** a second candidate exists with a meaningfully different value, classify the result as suspicious: still return the top candidate as the primary value (never leave the field blank when a pattern matched), but also return the runner-up as an alternative, and route the result through the existing "Save for later" path instead of the plain low-confidence banner.
- When `merchant_extractor.dart`'s top-2 candidates' confidences are within a small delta (provisional, not yet determined) of each other, treat as ambiguous: keep candidate #1 as the default but ensure both are available to the UI (they already are, via the existing top-5 list — this is a UI-surfacing decision, not a new extraction decision).
- When any confidence-aware extractor input (line confidence, word confidence, `digit_corrected`) is absent (older response shape, feature flag off, or the field genuinely wasn't populated), every extractor must behave exactly as it does today — confidence-aware terms default to a neutral (zero) contribution rather than being treated as a penalty for missing data.
- Never re-run `_calibrate_confidence` (or any other sigmoid squashing) on a value that already crossed the OCR API boundary as a calibrated number — word confidence, line confidence, and `ocrServiceConfidence` are all already-calibrated once they reach the client. This mirrors a real prior incident (`memory/bugs.md`): re-squashing an already-calibrated `ocrServiceConfidence` (0.34 → 0.036) caused false low-confidence flags. The same discipline applies to every new confidence value this feature introduces.
- Keep `ocrConfidence` (extraction-quality, computed by the parsers), `ocrServiceConfidence` (scan quality, from the OCR service), and the new line/word-level OCR confidence values namespaced and never conflated in code, naming, or documentation — this is the same category of bug the codebase has already shipped once.

## Edge Cases

- **High-confidence but incorrect OCR** (Tesseract is confident about a misread character): word-level confidence alone won't catch this — it's exactly why cross-check corroboration (subtotal reconciliation, cluster consensus) remains the primary defense, not confidence in isolation. This feature's confidence signal is a complement to, not a replacement for, the existing cross-check logic.
- **Low-confidence but correct OCR** (a genuinely unusual merchant name or item spelled correctly but scored low by Tesseract due to an unusual font/logo): the confidence-aware penalty should be soft (a scoring adjustment, not a hard filter) precisely so a correct-but-low-confidence result can still win when nothing else is more plausible — a hard confidence floor would make this case strictly worse than today.
- **Mixed-quality receipt** (crisp printed total, blurry/faded item list): line-level confidence already varies per line in this codebase's existing per-line calibration — this feature makes that variance usable for the first time rather than averaging it away in a single receipt-level number.
- **Numbers with low confidence but correct structure** (e.g. a price matching `\d+\.\d{2}` exactly but Tesseract wasn't sure of a digit): structural pattern match and OCR confidence are independent signals in this design — a struct-valid, low-confidence number is still eligible to win via cross-check corroboration, distinguishing "shape is right but I'm not sure of the digits" from "shape is wrong."
- **Merchant names with unusual spelling** (non-dictionary brand names, transliterated names): the existing `merchant_extractor.dart` already has no dictionary/spellcheck dependency (keyword/geometry/position based), so this feature doesn't introduce a new failure mode here — the added confidence term only matters when Tesseract itself was uncertain, not when the name is merely unusual but clearly read.
- **Word data present but line data missing, or vice versa** (a malformed/partial response, e.g. from a stale cached result or a server bug): client-side confidence-aware logic must treat any inconsistency as "confidence data unavailable" and fall back to today's behavior for that line, not crash or silently misattribute a word's confidence to the wrong line.
- **A digit-corrected word also has high OCR confidence** (Tesseract was "confident" about a character that still got substituted, e.g. a very clean "O" that's actually "0"): the `digit_corrected` flag applies its penalty regardless of the underlying confidence value — correction evidence and confidence evidence are independent inputs, not one derived from the other.
- **Every line on a receipt is below the enrichment threshold** (a uniformly poor scan): the LLM prompt's word-level tagging could, in the worst case, approach today's full-text size — bounded naturally since it's still one tag per word actually present, not a multiplier, but worth an explicit perf check (see Performance Considerations) rather than an unverified assumption that it stays cheap.

## Performance Considerations

- **Server-side CPU/memory:** retaining per-word tuples during the pass `_run_tesseract` already makes over Tesseract's output adds one more accumulator dict and one extra calibration call per word — same order of complexity as work already being done in that function, not a new pass over the image or a new Tesseract call. Memory overhead is a few hundred small tuples per receipt at most (typical receipts have on the order of 100–300 words) — negligible relative to the image buffers already held in memory during preprocessing.
- **Response payload:** bounded by the selective-enrichment design (only lines below the confidence threshold carry a `words` list) — well-scanned receipts see near-zero payload growth beyond the new (small) per-line confidence float; poorly-scanned receipts see growth proportional to how much of the receipt is actually uncertain, which is exactly the case where the extra detail earns its cost.
- **LLM prompt size:** the main understanding prompt gains one confidence tag per line (small, fixed overhead per line, same pattern the cleanup prompt already uses without issue) plus word-level tags only for already-enriched lines — must be checked against `MAX_OCR_PROMPT_CHARS` (existing 6000-char budget) the same way the cleanup path already checks it, since this feature makes the main prompt's size receipt-quality-dependent for the first time (today it's just truncated raw text with a fixed-shape overhead).
- **Client-side extraction latency:** the new scoring terms in each extractor are additional arithmetic on already-iterated candidates (no new passes over the OCR lines/words are needed beyond what each extractor already does) — expected to be an unmeasurable latency addition, but should still be included in whatever timing coverage the extractor tests already have, not assumed free without a check.
- **Not applicable:** no new network calls, no new caching concern (each receipt is unique, consistent with the sibling adaptive-OCR-strategy spec's same conclusion), no new server resource class (still single-process synchronous per request).

## Security Considerations

No new attack surface — no new external calls, no new persisted data beyond the existing OCR response, no new user input surface (the per-field UI indicators are read-only annotations on already-editable fields, not new input paths). The main consideration is defensive parsing of the new optional fields on the client: a malformed or unexpectedly-shaped `words` list (e.g. from a future incompatible server version) must fail safe to "no word data for this line" rather than throwing, consistent with this codebase's existing null-safe/optional-field conventions (e.g. `receipt_layout_analyzer.dart`'s `analyzeReceiptLayout` returning `null` rather than throwing on unmet preconditions).

## Tradeoffs

- **Word-level confidence surfaced to the client vs. kept entirely server-side (only used to enrich the LLM prompt).** Chosen: surface it (selectively), because the heuristic extractors run client-side and are the primary consumer named in the Problem Statement — keeping it server-only would mean the LLM path benefits but the heuristic path (which runs for every receipt, LLM or not, and which the LLM's own output is cross-checked against) would not. This does reverse the existing `OcrLine` docstring's stated rationale ("nothing downstream needs it") — flagged explicitly here since something now does, rather than silently contradicting that comment.
- **Selective per-line enrichment vs. always attaching full word-level detail to every line.** Chosen: selective, gated on line confidence. Always-attach is simpler to implement but grows response payload for every request regardless of whether any line actually needs the detail; selective enrichment costs a small amount of added conditional logic in exchange for bounding payload growth to exactly the receipts where it matters.
- **Confidence as an additive scoring term vs. a hard filter/threshold that excludes low-confidence candidates outright.** Chosen: additive/soft, everywhere. A hard filter would regress the "low-confidence but correct" edge case (a correct-but-uncertain reading would simply never be considered), and would duplicate rather than complement the cross-check corroboration this codebase already relies on as its primary redundancy mechanism.
- **Redesigning the top-level `combinedConfidence` blend vs. improving the `ocrConfidence` input that already feeds it.** Chosen: improve the input, per the explicit Non-Goal. The blend formula is a previously-tuned, small, legible piece of logic; reopening its weights would relitigate past tuning this feature has no new evidence to justify changing, whereas making its inputs more informed is strictly additive.
- **Character-level confidence vs. word-level.** Chosen: word-level, per the Non-Goals rationale — the existing digit-confusion-correction logic is already word/numeric-span-scoped, so word-level granularity already exposes exactly the unit of uncertainty that logic operates on; character-level would require a different Tesseract API call for benefit not yet demonstrated to be needed.

## Implementation Guidance

Suggested order of work:

1. **Server: retain and calibrate per-word data.** Modify `_run_tesseract` in `services/ocr-api/ocr_api/ocr_engine.py` to accumulate per-word `(text, raw_conf, left_ratio, width_ratio)` alongside the existing per-line accumulators, and attach a calibrated word list to `OcrLineResult` (new internal dataclass, e.g. mirroring `OcrLineResult`'s style). Do this first and in isolation — it has no dependency on the rest of the feature and is the foundation everything else builds on. Verify the existing line/request-level confidence numbers are bit-for-bit unchanged after this step (a regression here would silently break every threshold tuned against them).
2. **Server: flag digit corrections.** Adjust `_normalize_ocr_amounts` to operate per-word (word boundaries now survive past line-join) and mark corrected words. Inspect its current call site in `_run_tesseract` (called on `" ".join(words)` today) to restructure the call to operate before or alongside the join, not after.
3. **Server: extend `models.py` and the response shape.** Add the new public `OcrWord` model and `confidence`/`words` fields on `OcrLine`, implement the selective-enrichment threshold logic. Update `test_main.py`'s response-schema-stability test deliberately (same designed-guardrail pattern as the sibling adaptive-OCR-strategy spec) to the new expected superset shape.
4. **Server: extend the main LLM prompt.** In `receipt_understanding.py`, reuse `_build_cleanup_line_block`'s tagging pattern (or a shared helper factored out of it) for the main understanding prompt's line rendering, gated the same way as the client response's selective enrichment.
5. **Client: mirror the model changes.** Add `confidence`/`words` to `lib/domain/models/ocr_line.dart` and a new `OcrWord` model, matching the server shape field-for-field.
6. **Client: extend the three extractors.** Add the OCR-confidence scoring term to `rm_amount_parser.dart`, `merchant_extractor.dart`, `receipt_line_item_extractor.dart` as described in Technical Design — each is an additive term in an existing scoring function, not a rewrite. Extend `rm_amount_parser.dart` to return its full ranked candidate list (already computed, just not returned) to match `merchant_extractor.dart`'s existing multi-candidate shape.
7. **Client: wire suspicious-result classification and alternatives into `receipt_parse_pipeline.dart`**, adding the `merchantConfidence` top-level getter and exposing amount alternatives alongside the existing merchant candidates.
8. **Client: UI.** Add per-field low-confidence indicators and the ambiguous-candidate picker to `lib/features/share/receipt_confirm_sheet.dart`, replacing/supplementing the single generic `_NoticeBanner`.

Files to inspect before starting: `services/ocr-api/ocr_api/ocr_engine.py` (`_run_tesseract`, `_calibrate_confidence`, `_normalize_ocr_amounts`), `services/ocr-api/ocr_api/models.py`, `services/ocr-api/ocr_api/receipt_understanding.py` (`_build_cleanup_line_block`, `_build_messages`, `call_receipt_understanding`), `services/ocr-api/tests/test_ocr_engine.py` and `test_main.py` (existing fixture/test conventions), `lib/domain/models/ocr_line.dart`, `lib/domain/logic/rm_amount_parser.dart`, `lib/domain/logic/merchant_extractor.dart`, `lib/domain/logic/receipt_line_item_extractor.dart`, `lib/features/share/receipt_parse_pipeline.dart`, `lib/features/share/receipt_confirm_sheet.dart`, `memory/bugs.md` (the double-calibration incident this feature must not repeat).

Risks to watch: accidentally changing the existing line/request-level confidence numbers while adding word-level calibration (step 1's regression check exists specifically to catch this); re-introducing the double-calibration bug class on any of the new confidence values; the response-schema-stability test failing on this change is expected and must be updated deliberately, not bypassed; provisional thresholds (enrichment cutoff, suspicious-result confidence floor, ambiguous-candidate delta) being mistaken for final tuned values before dataset evaluation.

## Testing Strategy

- **Word-level retention unit tests:** synthetic Tesseract-output fixtures with known per-word confidences, asserting the retained word list matches expected text/confidence/position, and that line/request-level means are unchanged from their pre-feature values (the regression check named in Implementation Guidance).
- **Digit-correction flagging unit tests:** fixtures with known confusable-character substitutions, asserting `digit_corrected` is set exactly on the corrected words and not on unrelated words in the same line.
- **Selective enrichment unit tests:** fixtures spanning both sides of the enrichment threshold, asserting `words` is populated only for below-threshold lines.
- **Extractor scoring unit tests:** for each of the three extractors, fixture cases with identical text/geometry but varying injected confidence values, asserting the confidence term moves the score in the expected direction without overriding strong cross-check corroboration (a direct test of the "corroborated-but-uncertain still wins" decision-logic rule).
- **Suspicious-result classification tests:** constructed cases matching each of the three suspicious-result conditions (low confidence, no corroboration, plausible alternative) individually and in combination, asserting the classification only triggers when all three hold.
- **Field-level accuracy measurement:** extend the batch-tool dataset evaluation (shared harness with the sibling adaptive-OCR-strategy spec) to score amount/merchant/line-item accuracy individually against ground truth, not just aggregate OCR text accuracy — this feature's stated goal (protect *critical fields*) is only verifiable at field granularity, not receipt granularity.
- **Error detection / calibration check:** on the same labeled dataset, measure whether predicted low-confidence correlates with actual field-level incorrectness (a basic calibration curve) — this validates that the new confidence signal is doing its job, not merely that it exists.
- **Reduction in incorrect auto-accepts:** compare, pre- and post-feature, how often a field that's actually wrong in the labeled dataset would have been accepted without triggering any low-confidence signal — should decrease.
- **User correction frequency:** requires the event-tracking prerequisite named in Non-Goals; if absent, this metric is not measurable until that instrumentation exists — state this explicitly rather than assuming it's already collected.
- **Full regression:** existing extractor test suites (`merchant_extractor_test.dart`, `rm_amount_parser_test.dart`, `receipt_line_item_extractor_test.dart`) and OCR API test suites must pass unmodified except for the deliberately-updated schema-stability test.

## Rollout Plan

1. Ship server-side word retention and model extensions first, behind the same kind of opt-in env-var convention already used for `PREPROCESS_*`/`LLM_CLEANUP_ENABLED` (e.g. a flag gating whether `words`/line `confidence` are populated at all) — this lets the server-side change ship and be verified for the line/request-mean-unchanged regression before any client depends on the new fields.
2. Ship client-side model/extractor changes as additive: all new scoring terms default to zero contribution when the new fields are absent, so the client works unchanged against both old and new server responses during rollout.
3. Validate provisional thresholds (enrichment cutoff, suspicious-result floor, ambiguous-candidate delta) via the batch-tool dataset evaluation before enabling suspicious-result classification and the UI's alternative-candidate picker by default.
4. Enable the UI-facing per-field indicators and alternative-candidate picker last, once the underlying signal has been validated — these are the most user-visible pieces and the ones most likely to need threshold adjustment based on real data.
5. Backward compatibility throughout: every new field is optional and additive on both the server response and the client models; rollback at any stage is simply reverting the relevant flag/client build, with no data migration involved since nothing new is persisted to Drift or Postgres.
