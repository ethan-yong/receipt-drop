# Feature: Post-Share Receipt Notification (Interactive Quick-Note)

## Overview

When a user shares a receipt into Receipt Drop from another app (Maybank, Touch 'n Go, or an unrecognized source), the app currently saves the file silently to a local inbox and shows a one-line in-app toast — no acknowledgment persists once the user has switched away, and there is no way to attach context ("dinner with friends") without later opening the app and finding the right row. This feature replaces that toast with an OS-level interactive notification: an immediate "Receipt saved" acknowledgment, a best-effort named source ("Maybank receipt is processing") when identifiable, and an inline text field + Update action that lets the user attach a note at the moment they think of it, without opening the app.

## Problem Statement

`ShareIntentListener._handleSharedFiles` (`lib/features/share/share_intent_listener.dart`) saves the shared file to the `pending_imports` Drift table and calls `PlatformFeedback.showMessage(...)`, an in-app SnackBar-style toast. Once the user backgrounds Receipt Drop (the near-universal case — sharing happens *from* another app), that acknowledgment is gone forever; the only durable trace is a home-screen banner ("N receipts waiting") the user must remember to check. There is currently no mechanism to:
- Persist an acknowledgment the user can see after switching apps (toasts don't survive backgrounding).
- Attach freeform context to a receipt at share time — `notes`/`note` does not exist anywhere in the schema (`transactions`, `pending_imports`, or their Postgres counterparts); this is new, not wiring up something latent.
- Identify which app a receipt was shared from — `PendingImportModel.sourceApp` and its full Drift/Postgres/UI plumbing already exist (`pending_imports.source_app` column, `pending_imports_repository.dart`, displayed in `pending_drop_indicator.dart` and `pending_imports_screen.dart`) but the field is **never populated**: `saveSharedReceipt()` accepts a `sourceApp` parameter that no call site passes.

## Goals

- Show a durable, OS-level notification immediately when a receipt is shared in, acknowledging receipt and (best-effort) naming the source app.
- Let the user attach a short note to that specific receipt directly from the notification, with no app-open required.
- Populate the already-plumbed-but-dead `sourceApp` field using real signal (Android share referrer + a curated provider allow-list), never a guess.
- Preserve "drop and forget": ignoring the notification must not change today's behavior — the receipt still lands in the inbox/review flow exactly as it does now.

## Non-Goals

- Auto-confirming or auto-saving a transaction from the notification flow. `ReceiptConfirmSheet` remains the only path that commits a `transactions` row — this was already explicitly decided against for batch shares (`docs/system/decisions.md`, "Unified, batch-aware `ReceiptScanProcessingScreen`", 2026-07-21: "auto-saving each batch receipt as soon as OCR finished ... rejected by the user; conflicts with 'confidence scores tune the parser, not the user's mood'"). This feature does not reopen that decision.
- Editing merchant, amount, or category from the notification. The only notification-level input is the free-text note.
- Rich push notifications, remote/server-sent notifications, or any new backend service. Everything here is a **local** (on-device) notification triggered by the share event — no Supabase Edge Function or push infrastructure is involved.
- A general-purpose notification center or in-app notification history — this is one specific interactive notification tied to one pending import.
- Guessing a source app from content heuristics when no confident signal exists (explicitly called out by the user: "Do not attempt to guess the provider").
- Reworking the `Impact Drops/` gamification notification concepts, if any exist there — out of scope, this is capture-flow only.

## Proposed Solution

Two additive layers on top of the existing pending-import pipeline, both reusing dependencies already declared in `pubspec.yaml` but currently unused in `lib/`: `flutter_local_notifications: ^17.2.3` (zero call sites today outside generated plugin registrants) and the share-intent metadata already flowing through `receive_sharing_intent: ^1.8.0`.

1. **Source identification at share time.** On Android, read the sharing app's referrer package (via `Activity.getReferrer()`, which requires a small native addition since `receive_sharing_intent` doesn't expose it) and map known package names to display names through a small curated allow-list (Maybank, Touch 'n Go, extensible). No match → `sourceApp` stays `null`, exactly like today. iOS's share surface does not expose a reliable equivalent (see Technical Design) — `sourceApp` is `null` on iOS at share time; it may still be *inferred* later, non-blockingly, in step 3.
2. **Immediate acknowledgment notification.** The moment a file is saved to `pending_imports` (already instant, already offline-safe), post a local notification: title "🧾 Receipt saved", body naming the provider if known or the generic fallback if not, with a `RemoteInput`/text-input action ("Add a note", placeholder "Dinner with friends") and an "Update" submit action — no navigation, no app foregrounding.
3. **Background processing kicked off automatically**, decoupled from the existing `ReceiptScanProcessingScreen` UI: `ReceiptIngestService.ingestPath(...)` (already UI-independent — it takes only a path/mimeType/progress-notifier, no `BuildContext`) runs headlessly right after the file lands in the inbox, producing a parsed draft that is cached (not committed) against the `pending_imports` row. If this later resolves a confident merchant name matching the same provider allow-list, and `sourceApp` was null, the notification is updated in place to name the provider — still without opening the app.
4. **Inline note capture.** Submitting the notification's "Update" action writes the note text straight to the `pending_imports` row (a new column) through a background entry point — no full app launch on Android; iOS has real reliability constraints here that need a spike (see Edge Cases/Tradeoffs). When the user eventually opens the pending import (via `PendingImportsScreen`, the home banner, or by tapping the notification body itself), the cached draft and the note both pre-fill `ReceiptConfirmSheet`, which is still the only path that commits a transaction — the note is written to a new `transactions.notes` column at that point.
5. **Ignoring the notification changes nothing.** The receipt still sits in `pending_imports` with a completed background draft cached (or, on OCR failure, in today's `'failed'`/`'local'` state, still retryable from `PendingImportsScreen`) until the user opens the app.

Given the auto-OCR-on-share behavior in step 3 is a meaningful reversal of a deliberate 2026-07-21 decision to move OCR off the share path (see `docs/system/decisions.md` and `.claude/context.md`), it is scoped as an explicit, separately-flaggable increment — see Rollout Plan.

## User Experience

**Golden path, source identified (Android, Maybank installed and used to share):**
1. User taps Share → Receipt Drop from within the Maybank app on a transaction receipt screen.
2. Receipt Drop's share-intent handler saves the file to the inbox (as today) and, additionally, resolves `sourceApp = 'Maybank'` from the Android referrer + allow-list.
3. Within roughly a second, an OS notification appears: "🧾 Receipt saved" / "Maybank receipt is processing", with an "Add a note" text field and an "Update" button, while the user is still inside (or has already left) the Maybank app.
4. User types "Dinner with friends" and taps Update, without ever switching to Receipt Drop.
5. The note is persisted locally; the notification collapses to a quiet confirmation (e.g. "Note added") or is dismissed — no further interruption.
6. Later, the user opens Receipt Drop (any entry point) and reviews the pending import: `ReceiptConfirmSheet` opens pre-filled with the parsed merchant/amount/category **and** the note, ready to confirm.

**Source not identified (iOS, or an unrecognized Android app):**
Same flow, body reads "Your receipt is processing" instead of naming a provider. If background parsing later confidently recognizes a known provider's name printed on the receipt itself, the notification body may update to name it (still non-blocking, no guess presented if confidence is low).

**User ignores the notification entirely:** identical to today's behavior once the note-writing step is excluded — the file sits in the inbox; the home banner ("N receipts waiting") is unchanged; `PendingImportsScreen` shows it with Process/Retry as it does now, except the background draft is often already cached, so opening it feels instant instead of waiting through the OCR animation again.

**Background processing fails:** the notification updates to a neutral state (no provider claim, no "processing" claim) — something like the existing generic "Receipt saved" wording — and the pending import falls back to today's `'failed'`/retry path inside the app. The user is never shown an error inside the notification itself; errors are surfaced only when they open the app, consistent with the existing review-queue philosophy ("never silently zero/drop a receipt").

**Multi-file batch share:** a single grouped notification ("3 receipts saved — processing"), not one interactive notification per file. Per-file inline note capture is out of scope for batch shares in this iteration (see Decision Logic and Tradeoffs) — tapping the grouped notification opens `PendingImportsScreen`.

## System Impact

- **Client application**: new native-channel code (Android `MainActivity` addition to surface the share referrer; iOS notification-action wiring), a new background-processing entry point invoked from the share path, `flutter_local_notifications` initialization/permission-request code (none exists today), changes to `ShareIntentListener`, `PendingImportService`/`PendingImportsRepository`, and `ReceiptConfirmSheet` (new note field).
- **Database/storage**: Drift schema bump (new `note`/`draft_json` columns on `pending_imports`, new `notes` column on the local transactions table) and a corresponding Postgres migration (`notes` on `transactions`, `note`/an equivalent on `pending_receipts`) plus RLS coverage consistent with existing per-user policies.
- **AI/ML pipeline**: `services/ocr-api` (Tesseract + LLM understanding) is now invoked automatically for every share-in receipt, not only when the user taps Process — see Performance Considerations for the load implication.
- **Infrastructure**: no new services; the self-hosted `ocr-api`/LLM gateway on the existing MicroK8s cluster absorbs additional, less-predictable call volume (fire-and-forget from every share, whether or not the user ever opens the app to confirm).
- **External integrations**: none — no push notification service, no third-party dependency beyond the two packages already in `pubspec.yaml`.

## Technical Design

**Source identification.** `receive_sharing_intent`'s `SharedMediaFile` carries path/type/mimeType/message but not an originating package — confirmed by inspecting current usage in `share_intent_listener.dart`, which never reads any such field. Two platforms, two different ceilings:
- **Android**: `Activity.getReferrer()` returns an `android-app://<package>` URI reflecting the app that started the sharing `Intent`, independent of `startActivityForResult` (unlike `getCallingPackage()`, which doesn't apply to `ACTION_SEND`). This requires a small native addition (Kotlin, in `MainActivity` or a thin dedicated `MethodChannel`) since the Dart-side plugin doesn't expose it — read once per share event, passed down alongside the existing shared-media stream.
- **iOS**: standard Share Extension / `UIActivityViewController` targets are not told which app initiated the share; there is no reliable per-share source signal available before OCR. `sourceApp` is `null` at share time on iOS unconditionally — the feature must be fully functional with an always-null source on this platform (generic message only, at share time).

A curated, in-app static map (package name/bundle-id → display name, seeded with Maybank and Touch 'n Go and extensible without a schema change) turns a resolved referrer into a display string; anything not on the map is treated as unidentified, matching "should not attempt to guess."

**Deferred/optional refinement.** Once the background draft (see below) produces a merchant name via the existing heuristic + LLM merchant-candidate pipeline (`receipt_parse_pipeline.dart`), if that name confidently matches the same curated provider list (a substring/normalized match against the existing `MerchantCandidate.confidence`, reusing thresholds already tuned for the review-queue decision), the notification can be updated in place to name the provider even when the referrer signal was unavailable (iOS, or an unmapped Android package). This reuses existing parse-confidence machinery rather than inventing a new one.

**Background OCR trigger.** `ReceiptIngestService.ingestPath` already runs independent of any `BuildContext` — today it's invoked inside an unawaited `Future` from `PendingImportService.processImport`, itself gated behind the user tapping Process. The new path calls the same service directly from the share-intake path (or a thin wrapper around it), without the `ReceiptScanProcessingScreen` UI, producing a `ReceiptIngestDraft` that is serialized and cached against the `pending_imports` row instead of being handed to `ReceiptConfirmSheet` immediately. `PendingImportsScreen`'s existing Process action is updated to check for a cached draft first and skip straight to `ReceiptConfirmSheet` if one is fresh, falling back to a live OCR run if the cached draft is missing/stale (e.g. background processing failed or never completed).

**Notification lifecycle.** One `flutter_local_notifications` notification per single-file share, keyed by a stable ID derived from the `pending_imports` row ID so it can be *updated in place* (provider name arriving late, note-added confirmation) rather than stacking duplicates. A multi-file share instead posts one grouped/summary notification (see Decision Logic) tied to the batch, not to any single row.

**Inline note write path.** The `RemoteInput`/text-action response must be handled without assuming the Flutter engine/UI is live:
- Android: `flutter_local_notifications` invokes a background callback in a separate isolate (`@pragma('vm:entry-point')`), which must independently initialize plugin bindings before touching the Drift (native `dart:ffi` SQLite) connection — a minimal bootstrap, not the full `main.dart` app bootstrap (routing, theming, analytics are irrelevant here and would slow/complicate the callback).
- iOS: text-input notification actions are supported by the plugin, but reliably handling them while the app process is suspended or terminated is a materially different problem (background execution guarantees for local-notification actions are narrower than Android's); this needs a short platform spike before committing to "never opens the app" as a hard guarantee on iOS specifically (see Edge Cases, Tradeoffs).

**Schema.** `pending_imports` (Drift) gains a nullable `note` column and a nullable `draft_json` column (the cached parsed draft, serialized). `transactions` gains a nullable `notes` column, mirrored in Postgres via a new migration file (following the existing chronological pattern in `supabase/migrations/`) with the same per-user RLS shape already used for `transactions`. The note travels: notification → `pending_imports.note` → (on confirm) `transactions.notes`; the cached draft travels: background OCR → `pending_imports.draft_json` → (on open) pre-fills `ReceiptConfirmSheet`, then is discarded once the row is deleted (existing delete-on-save behavior in `PendingImportsRepository.delete`).

## Decision Logic

- When a single file is shared in: save to `pending_imports` (unchanged) → attempt Android referrer resolution → if resolved package is in the curated allow-list, set `sourceApp` to its display name; otherwise leave `sourceApp` null (never store/display an unmapped raw package name as if it were an identified provider).
- When the file is saved: post the interactive notification immediately, before OCR starts. Body = "`{sourceApp}` receipt is processing" if `sourceApp` is non-null, else "Your receipt is processing".
- Immediately after posting the notification: start background OCR (`ReceiptIngestService.ingestPath`) for that file, independent of notification state.
- If background OCR succeeds and `sourceApp` was null, and the resulting top merchant candidate confidently (existing confidence threshold used elsewhere in the parse pipeline — not a new bar invented for this feature) matches a curated provider name: update the notification body to name that provider. If `sourceApp` was already non-null, leave the body as-is (referrer signal takes priority over inferred-from-content, since it was gathered independent of receipt content and is not lowered by a noisy OCR pass).
- If background OCR fails or the file can't be parsed: leave `pending_imports.status` exactly as today's manual-trigger failure path would (`'failed'`/`'local'`), and drop the "processing" language from the notification (update to a neutral "Receipt saved" with no processing claim) rather than asserting a state that isn't true.
- If the user submits a note via the notification's Update action: write it to `pending_imports.note` for that specific row, regardless of whether background OCR has finished — the note and the OCR draft are independent and race-free (separate columns, separate writers). An empty/whitespace-only submission is a no-op (do not overwrite an existing note with blank text).
- If the user taps the notification body (not the note action): open the app directly to that pending import's confirm flow — this is the one interaction explicitly allowed to foreground the app, and only because the user chose it.
- If more than one file is shared in the same OS share action: skip the per-file interactive notification path entirely and post one grouped notification for the batch instead (see Tradeoffs for why individual per-file inline-reply notifications were rejected for batches).
- If notification permission was denied (Android 13+ `POST_NOTIFICATIONS`, or iOS authorization declined): skip notification posting silently; fall back to today's in-app toast only. Do not re-prompt beyond the single OS-native permission dialogue; do not block the save/OCR pipeline on permission state.
- If the user opens `PendingImportsScreen`/taps Process on a row that already has a cached `draft_json`: skip straight to `ReceiptConfirmSheet` with the cached draft (no repeat OCR call, no repeat animation). If `draft_json` is absent or its schema/version is stale, fall back to running OCR live exactly as today.

## Edge Cases

- User shares the same receipt file twice in a row before the first notification is dismissed — the second share must produce a second `pending_imports` row and a second notification with a distinct stable ID; must not silently merge or overwrite the first row's note/draft.
- User types a note and taps Update, but the background OCR draft fails a moment later — the note must survive (it's a separate column write) even though the "processing" claim in the notification becomes stale; the notification updates to the neutral/failed state without discarding the already-saved note.
- Android OEM notification-history/restore: some OEMs restore old notifications after a reboot with stale `RemoteInput` state — a note "Update" firing against a `pending_imports` row that was already deleted (transaction already confirmed and the row removed) must be a safe no-op, not a crash or an orphaned write.
- iOS: app fully terminated (swiped away) before the user taps Update — text-input notification actions may not reliably reach a background handler in this state; needs a pre-implementation spike to confirm actual behavior on target iOS versions. If unreliable, the documented fallback is: tapping Update briefly launches the app (rather than handling in true background), writes the note, and returns focus to the previous app — a degraded but still non-blocking experience, to be decided after the spike (see Tradeoffs).
- Android background isolate cannot access `Supabase.instance.client.auth.currentUser` because the auth client was never initialized in that isolate — the minimal background bootstrap must explicitly re-initialize whatever local session state is required to resolve the same `userId` as the main app (`Env.skipAuth` demo-user fallback covers the no-auth dev case, as it does today), or fall back to writing under a placeholder resolved the same way `PendingImportService._resolveUserId()` does today.
- Notification permission is denied *after* previously being granted (user revokes it in system settings) — subsequent shares must detect this and silently degrade to toast-only, not throw or repeatedly attempt to post.
- A multi-file batch share where only some files are recognizable images/PDFs and others are filtered out (mirrors today's `_handleSharedFiles` filtering) — the grouped notification's count must reflect only the files actually enqueued, not the raw share payload count.
- Referrer resolution returns a *chooser*/intermediate package (some OEM share sheets rewrite the referrer to their own package rather than the true origin app) rather than the actual source app — since this is inherently unreliable, it reinforces treating referrer-based identification as best-effort only, never authoritative, and never surfaced as a guess beyond the curated allow-list match.

## Performance Considerations

- **Latency**: the notification itself must appear near-instantly after the share intent is received (target: comparable to today's toast, which appears immediately since it doesn't wait on any network/OCR call) — it must be posted *before* OCR starts, not after.
- **Backend load**: today, OCR/LLM calls only happen when a user explicitly taps Process — many shared receipts are likely abandoned before that. This feature calls `services/ocr-api` (Tesseract + synchronous LLM understanding) for **every** share-in receipt automatically, whether or not the user ever opens the app again. This is a real, uncapped increase in call volume against a single-node, self-hosted cluster (see `docs/system/architecture.md`'s production hosting section) and against the shared LLM gateway — worth validating actual throughput headroom before enabling this unconditionally (see Rollout Plan).
- **Battery/CPU**: background OCR work runs opportunistically right after a share; on a device with no active network at that moment, the existing retry/backoff behavior of the OCR call path applies (same as today's manual-trigger failure handling) — no new polling loop is introduced.
- **Storage**: `draft_json` on `pending_imports` adds a small (single-receipt-sized) payload per pending row, discarded when the row is deleted — negligible compared to the receipt image/PDF already stored there.

## Security Considerations

- **Lock-screen exposure**: the notification body may include a note the user typed (e.g. "Dinner with friends") and the merchant/provider name — mildly sensitive but not financial amounts (the amount is never shown in the notification). Default OS notification visibility is likely acceptable, but this should be an explicit, reviewed choice rather than an accidental default, given this is a financial-tracking app.
- **Referrer spoofing**: Android's `getReferrer()` is set by the sending app and is not cryptographically verified — a malicious app could claim to be Maybank's package name in principle (package names themselves are not spoofable at the OS level since Android enforces unique signing per package, but this is worth a one-line confirmation during implementation, not an assumption). Regardless, source identification here only ever drives a *display label*, never an authorization or trust decision, so the blast radius of a spoofed referrer is cosmetic (wrong provider name shown), not a security boundary.
- **Background isolate auth context**: the Android background write path must resolve the same user identity the foreground app would, without accidentally writing under the wrong user's local row (relevant mainly in shared-device/dev-with-`Env.skipAuth` scenarios) — see Edge Cases.
- No new network-facing surface is introduced; all new writes are local-first (Drift), consistent with existing patterns, before any best-effort Supabase sync.

## Tradeoffs

- **Auto-triggering OCR on every share vs. keeping the manual Process gate.** The literal requested UX ("Maybank receipt is processing") implies OCR starts automatically, which is what's designed here — but this reverses a deliberate, recent decision (`.claude/context.md`: the share flow was moved from "immediate OCR" to an inbox/manual-Process pattern specifically to avoid a blocking/always-on OCR call per share). The alternative — ship only the notification + note-capture shell, keep OCR manual, and phrase the notification as "Receipt saved — add a note" without any processing claim — is lower-risk and reversible, but doesn't match the requested copy. Recommendation: ship the notification/note shell first (low risk, no backend load change), gate automatic background OCR behind a flag validated against real `ocr-api`/LLM throughput before enabling for all users (see Rollout Plan).
- **Per-file interactive notifications for batch shares vs. one grouped notification.** Individual per-file notifications with inline reply were considered for batches too, but this echoes the exact anti-pattern already rejected once (`docs/system/decisions.md`, 2026-07-22: "N celebrations" for batch saves read as broken/spammy) and adds real complexity (N simultaneous background note-writers, N notification IDs to manage, unclear what "processing" even means aggregated). A single grouped notification for batches, with full per-item detail only after opening the app, is simpler and consistent with that precedent.
- **Content-based source inference (post-OCR) vs. referrer-only.** Relying solely on the Android referrer would leave iOS and unmapped Android apps permanently generic. Layering in a confidence-gated post-parse merchant-name match (reusing existing parse confidence, not a new heuristic) recovers some identification on iOS and for unmapped apps, at the cost of the notification's provider label potentially changing after the fact (mitigated by only ever upgrading null→named, never overwriting an already-named source).
- **True background note-write vs. "tap opens app briefly."** The requested UX wants zero app-opening, full stop. Android supports this cleanly via `flutter_local_notifications`'s background isolate callback. iOS's guarantees here are weaker and need verification; falling back to a brief, invisible-as-possible app launch on iOS only (if the spike shows the pure-background path is unreliable) trades a small deviation from the ideal UX for actually working, versus shipping something that silently drops notes on certain iOS versions/states.

## Implementation Guidance

Suggested order of work:
1. **Schema first**: Drift migration adding `note`/`draft_json` to `pending_imports` and `notes` to the local transactions table (bump `schemaVersion`, add the migration branch per the existing pattern in `lib/data/local/app_database.dart`); companion Postgres migration in `supabase/migrations/` for `transactions.notes` and the `pending_receipts` equivalent.
2. **Notification plumbing shell** (no auto-OCR yet): initialize `flutter_local_notifications` (channel setup, Android 13+ `POST_NOTIFICATIONS` permission request — not currently declared in `android/app/src/main/AndroidManifest.xml`, needs adding — plus iOS authorization request), wire `ShareIntentListener` to post the acknowledgment notification with the text-input + Update action, and get the inline-reply write path working end-to-end (Android background isolate entry point writing to `pending_imports.note`). Validate this in isolation before touching OCR triggering.
3. **Source identification**: small native Android addition to surface `getReferrer()`, the curated package→display-name allow-list, and finally wiring `saveSharedReceipt(..., sourceApp: ...)` — note this call site (`share_intent_listener.dart`) already has the parameter ready to receive a real value.
4. **Background OCR trigger + draft caching**: decouple `ReceiptIngestService.ingestPath` invocation from `ReceiptScanProcessingScreen`, cache the resulting draft on the `pending_imports` row, and update `PendingImportsScreen`'s Process action to consume a cached draft when fresh. Land this behind a flag given the backend-load tradeoff above.
5. **Provider-name upgrade from parsed content** (null→named), reusing existing merchant-candidate confidence.
6. **iOS spike** for background/terminated-state reliability of the text-input action — do this before finalizing the "never opens the app" claim for iOS specifically; it can run in parallel with steps 1–3.

Areas to inspect closely before starting: `lib/features/share/share_intent_listener.dart` (entry point), `lib/features/pending_imports/pending_import_service_io.dart` and `pending_imports_repository.dart` (where the new columns and note-write path attach), `lib/features/share/receipt_ingest_service_io.dart`/`receipt_ingest_service.dart` (confirm it's genuinely `BuildContext`-free all the way down before assuming it's background-isolate-safe), `lib/data/local/tables.dart` + `app_database.dart` (schema migration pattern), `android/app/src/main/AndroidManifest.xml` (missing `POST_NOTIFICATIONS`, and where to add the referrer-reading native code).

Real risks: the Android background isolate touching Drift's `dart:ffi`-based SQLite has not been done anywhere in this codebase yet — confirm this actually works reliably before building the rest of the feature on top of it, since every other background/sync mechanism here (`SyncWorker`) runs inside the live app process, not a plugin-spawned isolate. This is the single highest-uncertainty piece of the whole feature.

## Testing Strategy

- **Unit**: package→display-name allow-list mapping (known package → correct label; unknown → null, never a guessed label); note write-path idempotency (empty/whitespace submission is a no-op; resubmission overwrites cleanly); draft-cache staleness check (missing/old-schema `draft_json` correctly falls back to a live OCR run).
- **Integration (Drift)**: migration correctness for the new columns on both `pending_imports` and the transactions table, including upgrade-from-prior-schema-version paths (mirroring how existing schema bumps are tested, if such tests exist — otherwise this is a new precedent worth establishing given the note/draft data must survive an app update).
- **Platform-specific (manual/device, since these depend on OS notification behavior that's hard to unit test)**: Android — share from a real Maybank-package-mimicking test app to confirm referrer resolution; submit a note while the app is fully force-stopped, confirm the background isolate write succeeds and Drift is consistent afterward; deny notification permission and confirm graceful fallback to the existing toast. iOS — confirm actual behavior (not assumed) for text-input notification actions when the app is backgrounded vs. terminated, which is precisely the open question the spike in Implementation Guidance step 6 needs to resolve before this is called done on iOS.
- **Regression**: existing single- and multi-file share-to-inbox flow (`PendingImportsScreen` Process/Retry/Process-all) must continue working unchanged when the new background-OCR flag is off, and when a cached draft is present, must reach the same `ReceiptConfirmSheet` state as a live OCR run would.
- **User acceptance criteria**: sharing a Maybank receipt while the app is backgrounded produces a notification naming Maybank within roughly a second, without foregrounding Receipt Drop; typing a note and tapping Update does not open the app on Android; ignoring the notification entirely still results in the receipt appearing in `PendingImportsScreen` exactly as it does today.

## Rollout Plan

Ship in the staged order implied by Implementation Guidance, each stage independently shippable and reversible:
1. Notification shell + inline note capture, OCR still manual (today's behavior) — lowest risk, no backend load change, immediately gives the "feels like a messaging app" acknowledgment and note-taking value even before auto-processing exists.
2. Source identification (Android referrer + allow-list) — additive, no behavior change if it fails to resolve (falls back to today's generic wording).
3. Automatic background OCR triggering, behind a remote/local feature flag, enabled for an internal/small cohort first specifically to observe `ocr-api`/LLM gateway load under the new always-on-share call pattern before wider rollout — this is the stage with the real infrastructure-load unknown.
4. iOS background note-write, gated on the spike's outcome; if unreliable in the terminated-app case, ship the "brief app launch" fallback for iOS only rather than blocking the whole feature on it, clearly documented as a platform-specific deviation from the Android behavior.

Rollback: each stage can be disabled independently via its flag without data loss — `note`/`draft_json` columns are additive and harmless if a stage is turned back off; the existing manual Process/Retry path in `PendingImportsScreen` remains fully functional as the fallback for all of them.
