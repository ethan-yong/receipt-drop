# Feature: Feedback Learning System for Receipt Parsing

## Overview

Capture the predicted-vs-confirmed pairs that already exist momentarily in `receipt_confirm_sheet.dart`'s widget state whenever a user edits a merchant name, amount, category, or line item, and use them to improve future predictions through three deterministic, explainable learning surfaces scoped to match the sensitivity of the underlying data: a global merchant-identity cache (extending the existing `merchant_aliases` table), a per-user category-preference table, and an anonymized, pattern-only global table for systematic OCR-misread detection. No trained model is introduced anywhere — every mechanism here is a frequency count or lookup-table update, consistent with this codebase's existing heuristic-over-ML posture.

## Problem Statement

1. **Corrections vanish today.** In `receipt_confirm_sheet.dart`, `_commitVendor()` and `_commitPriceEdit()` overwrite `_vendorName`/`_prices[i]` in place with no original-value twin kept; `_editedDraft()`'s `copyWith` then overwrites the draft's `merchantRaw`/`lineItems` before the save payload is built. By the time a transaction reaches the local Drift outbox or syncs to Postgres, the original OCR/LLM prediction for merchant and line-item price is unrecoverable — only the final, already-corrected value survives. Category is the one exception: `categoryGuess` and `categoryUser` are stored side by side, unused as a learning signal today despite already existing on every transaction with an explicit user category.
2. **Merchant resolution can repeat the same mistake forever.** `enrich-transaction`'s alias write-back (`upsert_merchant_alias()`) only fires when Google Places itself auto-resolves with confidence ≥0.85. A user's explicit correction — a free-text merchant-name edit, or a `place_status='user_locked'` override via the place picker — never reaches `merchant_aliases`, so the next receipt from the same merchant (for that user, or any other user near the same location) gets the same wrong auto-resolved guess again.
3. **No systematic-misread detection exists anywhere.** `_normalize_ocr_amounts`'s digit-confusion table (Z/z/O/l/I → 2/2/0/1/1) is a fixed, hand-written set with no feedback loop from real corrections telling it what Tesseract actually gets wrong in practice, at what rate, or whether the fixed set is even complete.
4. **Category-guess accuracy has no feedback signal.** Despite `category_guess` vs. `category_user` divergence already being recorded on every transaction, nothing consults that history to improve the guess for a user's recurring merchants — a large pool of already-collected, currently-unused signal.

## Goals

- Capture a predicted-vs-confirmed correction record for merchant, amount, category, and line-item fields at the exact point in `receipt_confirm_sheet.dart` where both values are still simultaneously in scope, before the existing overwrite.
- Extend the existing `merchant_aliases` global cache to write back from explicit user corrections (free-text edits, `user_locked` picker overrides), not only from auto-resolved high-confidence Places matches — reusing the existing table, RLS shape, and `place_matching.ts` normalization primitives rather than building parallel infrastructure.
- Build a per-user `(merchant, category)` preference signal from captured corrections, including a one-time backfill from the `category_guess`/`category_user` divergence already sitting in existing `transactions` rows.
- Build an anonymized, pattern-only cross-user aggregate for systematic OCR-misread detection, with the abstraction from raw correction to anonymized pattern happening before any data leaves per-user-scoped storage — the actual privacy guarantee, not merely an RLS policy applied after the fact.
- Feed all three learned signals into the existing extractors/prediction paths as additional ranking/confidence inputs, never as a silent override of a strong live signal.
- Ensure a bad or mistaken correction degrades at most its originating user's own personalized signal — never the shared global signal — without requiring a moderation/review step, via corroboration-gated trust tiers.

## Non-Goals

- **No trained ML model** (embeddings, classifiers, neural nets) anywhere in this feature — deterministic frequency counts and lookup tables only, consistent with the standing heuristic-over-ML precedent.
- **No raw per-user financial data in any cross-user/global table.** Only derived, anonymized patterns cross the per-user boundary for the misread-pattern surface, per the resolved cross-user-scope decision.
- **No retroactive recovery of already-lost historical merchant-name or line-item-price corrections** — those originals are unrecoverably overwritten already (confirmed by inspecting the current save pipeline). Learning captures from this feature's ship date forward for those two fields. Category is the exception, since `category_guess`/`category_user` already coexist and can be backfilled for free.
- **No change to the LLM understanding/cleanup call count, precedence rules, or prompt structure** beyond what the sibling token-confidence-tracking spec already covers — this feature is an additional signal source feeding the same extractors, not an LLM-integration redesign.
- **No dedicated "feedback"/"training" UI.** Corrections are captured passively from the existing inline-edit affordances on the confirmation screen — no new screen, prompt, or opt-in flow.
- **No real-time re-ranking of the receipt currently being edited.** A correction is only reflected starting the *next* receipt that touches the same merchant/pattern — there is nothing left to re-predict on the receipt the user just told you the right answer for.
- **No change to `place_status='user_locked'`'s existing terminal-override semantics** for that one transaction — this feature adds a write-back side effect when that status is set, it doesn't change what the status itself does to that transaction.
- **No change to `updateTransaction()`'s existing edit path** (the transaction-detail-screen editor, separate from the confirm sheet) — corrections made there are out of scope for capture in this version (see Edge Cases); this is a stated scope boundary, not a silent gap.

## Proposed Solution

Three learning surfaces, each matched to the existing data-sharing precedent for its sensitivity class:

1. **Merchant identity (global, low-sensitivity)** — extend `merchant_aliases`' existing write-back path with a second trigger: an explicit user correction (free-text merchant edit, or a `user_locked` picker override) upserts into the same table via the same `upsert_merchant_alias()`-style definer function and the same `normalizeForCompare()`/geohash keying `place_matching.ts` already uses, rather than a new parallel table.
2. **Category preference (per-user, personal)** — a new table keyed `(user_id, merchant_normalized)` recording the category the user actually confirmed, with a small corroboration-count gate before it's trusted, backfilled once from existing `category_guess`/`category_user` divergence and updated incrementally thereafter. Strictly owner-only RLS, matching `transactions`' own policy.
3. **OCR misread patterns (global, anonymized, pattern-only)** — a new global table, RLS-locked-down exactly like `merchant_aliases` (zero policies, definer-function-mediated access only), recording only abstracted character-substitution counts derived from amount/line-item corrections — the actual digits, amounts, and receipt content are discarded at the point of abstraction, before anything leaves per-user scope.

All three are consulted as additional ranking/confidence inputs by the existing extractors and correction logic, never as a silent override of a strong current-request signal (a high-confidence Places match or LLM read still wins).

## User Experience

- **Golden path:** unchanged — nothing new is visible when a receipt is captured and confirmed without edits.
- **Capture:** entirely passive, riding on the existing inline-edit affordances (tap-to-edit vendor name, tap price, category dropdown, place picker) — no new UI element, no "submit feedback" action.
- **Benefit on a later receipt:** a merchant or category the user (or, for merchant identity, any user) has previously corrected now appears pre-filled correctly instead of repeating the same wrong guess — visible only as "the app got it right," with no explicit "learned from you" messaging (consistent with the no-dedicated-feedback-UI Non-Goal).
- **Conflicting/inconsistent corrections over time:** resolved by recency (see Decision Logic) — the field stays editable regardless, so an imperfect learned prediction degrades no differently than today's imperfect heuristic/LLM prediction already does.
- **Error handling:** a correction that fails to sync (offline, outbox pending) must never block or slow the local save — correction capture rides the same local-first outbox pattern the transaction itself already uses, syncing opportunistically, never a blocking call.

## System Impact

- **Client application:** `receipt_confirm_sheet.dart` (capture hook before the existing overwrite), `receipt_ingest_draft.dart`/`ingest_receipt_request.dart` (new optional corrections payload), a new Drift table alongside `outbox_transactions`/`outbox_line_items` (named distinctly from the existing `ocr_corrections` column — see Implementation Guidance naming risk), `transaction_repository_native.dart`/`_web.dart`, `sync_worker_flutter.dart` (uploads pending corrections alongside the existing transaction sync); consumption sites in `merchant_extractor.dart` (alias/category-preference lookup) and wherever digit-confusion correction lives (misread-pattern lookup).
- **Backend services:** new Supabase migration(s) for the per-user category-preference table and the global misread-pattern table; extended `enrich-transaction` (or a small adjacent function) adding the user-correction write-back trigger into `merchant_aliases`; a mechanism for periodic/incremental misread-pattern aggregation (see Technical Design's online/offline treatment).
- **Database/storage:** two new tables (per-user category-preference; global misread-patterns) plus a new write path into the existing `merchant_aliases` table; new RLS policies following the two conventions this schema already establishes (owner-only vs. locked-down-global-with-definer-functions).
- **AI/ML pipeline:** no new model. Learned signals become additional inputs to existing heuristic extractors and digit-correction logic — no new or additional LLM call.
- **Infrastructure:** possibly a periodic aggregation job for the misread-pattern surface, depending on the online/offline design chosen (see Technical Design) — **assumption flagged**: this research pass did not confirm what scheduled-job infrastructure already exists in this Supabase project; verify during implementation rather than assuming a mechanism is available.

## Technical Design

**Capture hook.** `receipt_confirm_sheet.dart` already computes the exact diff flags this feature needs for other purposes: `_vendorEdited`, `_anyPriceEdited` (via `_prices[i] != _items[i].priceMyr`), `_anyExcluded`, and `_categoryOverride != null`. This feature adds one more step immediately before `_editedDraft()`'s `copyWith` overwrites the originals: for each flag that's true, emit a correction record `{field, predicted, confirmed, merchantNormalized, confidence, timestamp}` — reusing values already on `widget.draft`/`ReceiptParseResult` (`merchantRaw`, `merchantConfidence`, `categoryGuess`, `categoryConfidence`, each item's original `priceMyr` and `confidence`) as the "predicted" half, and the live widget-state value as the "confirmed" half. No new diffing logic is needed — only new *retention* of a diff the code already computes transiently.

**Transport and storage.** Correction records attach as an optional list on `IngestReceiptRequest`, persist to a new local Drift table (distinct name from the existing `ocr_corrections` column, which already means something unrelated — an LLM OCR-text-cleanup diff, not a user-edit record), and sync via `sync_worker_flutter.dart` alongside the existing transaction upload into a new Postgres table with owner-only RLS (`user_id = auth.uid()`, same policy shape as `pending_receipts_owner`/`transactions`). This table is the single source-of-truth event log every downstream learning surface derives from.

**Merchant-alias write-back.** A new trigger point — either a client-side call to a definer function mirroring `upsert_merchant_alias()`'s existing signature, or a Postgres trigger on the new corrections table filtering for merchant-field records — upserts the corrected value into `merchant_aliases`, keyed identically to the existing table (`normalizeForCompare()` + geohash bucket, reused from `place_matching.ts` rather than reimplemented). Trust tier differs by correction type (see Decision Logic): a `user_locked` picker override is a stronger, more deliberate signal than a quick free-text edit and is treated accordingly.

**Category-preference table.** New table `(user_id, merchant_normalized, category, correction_count, last_corrected_at)`, RLS owner-only. Backfilled once via a one-time script over existing `transactions` rows where `category_user is not null and category_user != category_guess` — free historical signal, no new capture needed for this part. Updated incrementally on every future confirm-sheet category correction.

**OCR-misread-pattern aggregation.** At correction-capture time, if the corrected field is amount or a line-item price, a diff-alignment step compares the predicted and confirmed numeric strings character-by-character. If they align closely enough to represent a small, localized fix (not a wholesale rewrite), the abstracted character-substitution pair(s) actually present (e.g., "class of character X was corrected to class of character Y") are emitted — with the actual digit values and the amount itself discarded before this record is constructed. If the two strings don't align confidently (structurally too different), nothing is emitted — a large mismatch is evidence the whole field was wrong for reasons unrelated to a specific OCR misread, not evidence of a misread pattern. This abstraction happens client-side (or in a per-user-RLS-scoped step) before the record ever reaches shared storage — the actual privacy guarantee, not an after-the-fact filter on a table that briefly held raw data. The abstracted pattern is then upserted (atomic count increment) into a new global table via a definer function, following `merchant_aliases`' exact revoke-from-public/grant-to-authenticated convention.

**Online vs. offline learning, by surface — and why the distinction mostly dissolves here.** Because nothing in this design is a trained model, there is no separate "training pass" to be online or offline about — every surface is a running counter or cache entry, updated at write time and read at prediction time:
- *Merchant-alias write-back:* online/immediate — a direct user correction is treated as ground truth the moment it syncs, no aggregation gate needed before trusting it (matching how the existing Places-auto-resolve path already writes immediately at confidence ≥0.85).
- *Category preference:* online/immediate per-user upsert — cheap (one small table, one user's own row), no cross-user aggregation risk to gate on, so batching would only add latency for no safety benefit.
- *Misread-pattern aggregation:* the abstraction step happens at capture time (online, per-correction), but the aggregate is only *meaningful* once enough corrections have accumulated — so while the write itself is immediate (an atomic increment, no batch job required for the write path), *consuming* the aggregate as a confident signal is effectively gated on volume, which is a read-time threshold check, not a distinct offline training step. If a periodic sweep proves useful later (e.g. for the data-quality review in Decision Logic), it would be the one genuinely batch-shaped piece of this design — flagged as optional, not required for v1.

## Decision Logic

- When a user changes a field's value away from its predicted value in the confirm sheet, capture a correction record for that field before the predicted value is overwritten; when a field is left unchanged, capture nothing (avoids flooding storage with "no correction" noise).
- When a `user_locked` place-picker override is captured, upsert into `merchant_aliases` unconditionally, at maximum confidence — picking a specific place from a picker is a deliberate, multi-step action, much less likely to be an accidental edit than a quick text change, and it already functions as a terminal per-transaction override today.
- When a free-text merchant-name edit is captured and it targets an alias-cache key that has **no established entry** (or one with a low `hit_count`), upsert it directly, same as today's ≥0.85-confidence auto-resolve path.
- When a free-text merchant-name edit is captured and it targets an alias-cache key that **already has an established entry** (hit_count above a small threshold, not yet numerically fixed — needs tuning) with a **different** canonical value, do not overwrite unconditionally — queue it as a competing low-weight candidate requiring a small number of corroborating corrections (mirroring the category-preference rule below) before it can displace an established entry. This is the feature's primary defense against a single bad free-text edit poisoning a table every user shares.
- When deriving a misread pattern from an amount/line-item correction, only emit the pattern if the predicted/confirmed strings align as a small, localized fix; emit nothing for a wholesale rewrite (see Technical Design) — never guess at an alignment that isn't confident.
- When applying the category-preference signal to a new prediction, only surface/prefer a learned category once it has been corrected consistently **at least twice** for that `(user, merchant)` pair — a single correction could be a one-off mistake. If two corrections for the same merchant disagree, keep the more recent one rather than averaging or picking the majority.
- When applying the misread-pattern signal to digit-confusion correction, use it only as a confidence adjustment/tie-breaker alongside the existing fixed substitution table — never let a learned pattern introduce a substitution outside the fixed table's already-scoped confusable-character set, since expanding that set algorithmically risks overcorrecting unrelated characters the fixed set was deliberately scoped to avoid.
- When any learned signal (alias, category preference, misread pattern) conflicts with a high-confidence current-request signal (a high-confidence Places match, a high-confidence LLM category read), the current-request signal wins. Learned signals only influence ranking among otherwise-close candidates, or fill in when the current-request signal is itself low-confidence — never override a strong live read.
- When a correction can't sync immediately (offline, outbox pending), it must not block or delay the local save — it queues in the same local-first outbox pattern as the transaction itself.
- When the misread-pattern table receives an update, it must go through the definer-function increment path, never a raw client write — mirrors `merchant_aliases`' access-control convention exactly, and is the mechanism that keeps the abstraction guarantee (Technical Design) enforceable rather than merely advisory.

## Edge Cases

- **New merchant with no history:** falls back to today's behavior exactly — no alias hit, no category preference, feature is purely additive; absence of learned data must never degrade a fresh prediction below today's baseline.
- **User with very little data:** the ≥2-correction corroboration gate means a brand-new user simply gets no personalization yet, rather than an unstable one-off-derived preference being applied prematurely.
- **Conflicting corrections over time** (user corrects a merchant's category to "Food," then later to "Groceries"): recency wins, per Decision Logic — documented explicitly so this isn't ambiguous behavior a future engineer has to guess at.
- **Shared devices / shared login:** the per-user preference table is keyed by `user_id` from auth, not device — a shared login mixes both people's corrections into one signal. This is an accepted limitation consistent with how the rest of the app already treats one authenticated session as one identity everywhere else; not a regression this feature introduces.
- **Multi-language receipts** (English/Malay, matching the existing `eng+msa` OCR config): merchant-alias and category-preference keys are normalized text and language-agnostic by construction (same normalization `place_matching.ts` already uses). Whether Malay text introduces different common misreads than the existing Latin-digit-confusion set is **not yet known** — flagged explicitly as needing real correction data before assuming the existing confusable-character set generalizes, rather than assumed to just work.
- **Bad-faith or mistaken correction targeting the global alias cache:** mitigated by the corroboration-gate tiering in Decision Logic (free-text edits require corroboration against an established entry; only picker overrides get unconditional trust) — this is the feature's answer to "preventing incorrect user edits from degrading the system," a real risk distinct from the per-user surfaces (whose blast radius is self-contained to the correcting user).
- **Rapid back-and-forth correction of the same field** (a user toggling a value, e.g. while testing): worst case under the recency-wins rule is a stale preference lagging by one step, not a functional bug — a dedupe of near-identical successive corrections within a short window is a reasonable implementation nicety, not a hard requirement.
- **Corrections made via `updateTransaction()`'s separate edit path** (transaction-detail screen, not the confirm sheet): invisible to this feature's capture hook, per the stated Non-Goal/scope boundary — flagged explicitly here again so it isn't mistaken for an oversight rather than a deliberate v1 scope limit.

## Performance Considerations

- **Capture cost:** negligible — reuses diff flags (`_vendorEdited`, `_anyPriceEdited`, `_categoryOverride != null`) already computed today for save-payload construction; building a correction record from already-diffed data is O(number of edited fields), not a new pass over anything.
- **Storage growth:** the category-preference table grows with a user's distinct-merchant diversity, small relative to their transaction history. The misread-pattern table grows with the (small, bounded by the existing confusable-character set) space of distinct substitution pairs — counts increment, rows don't multiply, so it plateaus quickly regardless of user or receipt volume. The `merchant_aliases` write-back reuses an existing table's existing growth characteristics; no new growth pattern is introduced there.
- **Query performance:** alias/category-preference lookups happen once per receipt at prediction time, against small indexed tables (mirroring `merchant_aliases`' existing unique-key-backed lookup). **Must be checked against the sibling adaptive-OCR-strategy spec's latency budget** if consulted synchronously during the `/ocr`-adjacent understanding step — a new synchronous round trip per receipt is not free, and should either be cached client-side, made non-blocking, or otherwise verified not to reopen that already-tight budget; flagged as an implementation decision requiring explicit verification, not assumed free.
- **Cross-user aggregation cost:** amortized off any single request's latency path (the write is an atomic increment; there's no batch retraining step to budget for, per the online/offline treatment above).
- **Scalability:** both new tables are small relative to `transactions`/`receipt_line_items` and grow sub-linearly in total receipt volume (per-distinct-merchant or per-distinct-pattern, not per-transaction) — no scaling concern distinct from the rest of the schema.

## Security Considerations

- **RLS/access-control split matches data sensitivity**, mirroring two conventions this schema already establishes: the per-user category-preference table gets `transactions`-identical owner-only RLS; the global misread-pattern table and the `merchant_aliases` write-back get `merchant_aliases`-identical locked-down RLS (zero policies) plus definer-function-mediated access, with the same explicit revoke-from-`PUBLIC`/grant-to-`authenticated` convention `memory/bugs.md` already warns not to skip.
- **Data minimization at the source is the actual privacy guarantee**, not an RLS policy applied after the fact — the abstraction from raw correction to anonymized misread pattern must happen before the event leaves per-user-scoped storage (client-side or a per-user-RLS-scoped step), never as a filter on a shared table that briefly held raw amounts.
- **Abuse case:** a malicious or compromised client submitting fabricated corrections to poison the global alias cache or misread-pattern table. Same risk class `merchant_aliases` already accepted for its existing write path (any authenticated user's high-confidence write is trusted); mitigated the same way (function-mediated writes only, no direct table grants) plus this feature's corroboration-gate tiering, rather than a new security model.
- **No new PII surface:** corrections don't introduce any personal-data field beyond what `transactions` already stores (merchant text, amount, category) — the new tables either strip identity entirely (misread patterns) or stay within existing per-user RLS (category preferences).

## Tradeoffs

- **Deterministic frequency/lookup tables vs. a trained ML model.** Chosen: deterministic, consistent with the standing heuristic-over-ML precedent. Even though correction data here is naturally labeled (unlike the OCR-layout case where "no labeled data" was the stated rejection reason), a hand-inspectable, reversible frequency table remains preferable for a financial-data product where a wrong learned adjustment needs to be diagnosable by inspecting a row, not by explaining a model's weights.
- **Anonymized pattern-only cross-user aggregation vs. strictly per-user-only learning for financial-field corrections.** Chosen: pattern-only aggregation, per the explicit resolved decision — trades a real implementation cost (the abstraction/alignment step) for meaningfully better systematic-misread detection than any single user's correction volume could provide alone.
- **Extending the existing `merchant_aliases` table vs. a new parallel "user-corrected aliases" table.** Chosen: extension. A parallel table would fragment merchant-identity resolution into two sources of truth that `enrich-transaction` would then need to reconcile every time; one table with two write paths (algorithmic ≥0.85 confidence, or corroboration-gated/unconditional on explicit correction) keeps a single source of truth, consistent with preferring incremental change over a parallel rewrite.
- **Real-time re-ranking of the receipt currently being edited vs. applying corrections starting the next receipt.** Chosen: next-receipt only. Re-running extraction mid-edit on the same receipt session adds real complexity for no real benefit — the user has already told you the right answer for that specific receipt; there's nothing left to predict on it.
- **Unconditional trust for all correction types vs. tiered trust by correction mechanism.** Chosen: tiered (picker overrides trusted immediately, free-text edits corroboration-gated against established entries). A single blanket "trust every correction" rule was considered and rejected because it would make the shared global alias cache trivially poisonable by one mistaken free-text edit — the tiering costs a small amount of added logic in exchange for closing that risk.

## Implementation Guidance

Suggested order of work:

1. **Client: capture hook.** Add correction-record construction to `receipt_confirm_sheet.dart`, immediately before `_editedDraft()`'s existing `copyWith` overwrite, reusing the already-computed diff flags (`_vendorEdited`, `_anyPriceEdited`, `_categoryOverride`). Build and test this in isolation first — it has no dependency on storage or server changes yet.
2. **Client: local storage and transport.** New Drift table (naming risk: pick a name clearly distinct from the existing `ocr_corrections` column, which already means an unrelated concept — LLM OCR-text-cleanup diffs, not user-edit records; e.g. `outbox_field_corrections`). Extend `ingest_receipt_request.dart`/`receipt_ingest_draft.dart` with the new optional payload; extend `transaction_repository_native.dart`/`_web.dart` to persist it.
3. **Client: sync.** Extend `sync_worker_flutter.dart` to upload pending correction rows alongside the existing transaction sync.
4. **Server: migrations.** New tables following this schema's exact conventions (`YYYYMMDDHHMMSS_snake_case_description.sql` filenames, `enable row level security` immediately, `<table>_<cols>_idx` index naming): `user_field_corrections` (owner-only RLS, mirrors `pending_receipts_owner`), `user_category_preferences` (owner-only RLS), `ocr_misread_patterns` (zero-policy + definer-function-only access, mirrors `merchant_aliases` exactly, including the explicit revoke/grant).
5. **Server: merchant-alias write-back.** Extend `enrich-transaction` (or a small adjacent function) to call an `upsert_merchant_alias()`-style path from the new correction write, reusing `place_matching.ts`'s `normalizeForCompare()`/geohash helpers rather than reimplementing them; implement the corroboration-gate tiering from Decision Logic here.
6. **Server: category-preference backfill.** One-time script (not a permanent migration) over existing `transactions` rows where `category_user is not null and category_user != category_guess`, populating the new table's initial state for free.
7. **Server: misread-pattern definer function.** Atomic-increment upsert function, following `upsert_merchant_alias()`'s revoke-then-grant convention exactly.
8. **Wire consumption.** Category-preference lookup into `merchant_extractor.dart`'s scoring / the `vendor_category` prediction path; misread-pattern lookup into the digit-confusion correction logic (`_normalize_ocr_amounts` server-side, and/or its client-side sibling if the token-confidence-tracking spec's design is also implemented).

## Testing Strategy

- **Capture unit tests:** constructed edit sequences in the confirm sheet, asserting a correction record is emitted only for genuinely changed fields, with the correct predicted/confirmed pair.
- **Alias write-back tests:** cases for both trust tiers (picker override vs. free-text edit against an established vs. unestablished alias entry), asserting the corroboration gate behaves as specified in Decision Logic.
- **Category-preference tests:** the ≥2-correction gate and recency-wins-on-conflict rules, table-driven over constructed correction sequences; a backfill test verifying the one-time script correctly derives preferences from existing `category_guess`/`category_user` divergence in fixture data.
- **Misread-pattern abstraction tests:** given known predicted/confirmed string pairs, assert the emitted pattern (or absence, for non-alignable diffs) matches expectation — and assert the actual amount value never appears anywhere in the emitted record, as a direct, automatable test of the privacy guarantee, not just a correctness check.
- **Improvement-over-time / correction-reuse-rate measurement:** since the corrections log this feature builds is itself the outcome measure, track — per learning surface — how often a previously-corrected `(merchant)` or `(user, merchant)` pair no longer needs correction on a subsequent receipt; this requires no separate instrumentation beyond what's being built.
- **Reduction-in-repeated-mistakes check:** for a given merchant/pattern, flag if the *same* correction recurs after the learned signal should already have fixed it — a direct regression signal pointing at a bug in the write-back or lookup path, not just "learning is imperfect."
- **A/B / holdout testing:** since corrections are observational (no way to run two parallel realities for one user's real spending), a feasible design is a holdout — withhold learned-signal application for a random subset of eligible `(merchant)`/`(user, merchant)` pairs and compare correction-recurrence rate between treated and holdout groups, using the corrections log as the outcome measure for both arms.
- **Full regression:** existing extractor and enrich-transaction test suites must pass unmodified except where deliberately extended for the new consumption sites.

## Rollout Plan

1. Ship the capture hook and local/synced storage first, behind a flag, with corrections captured and synced but **not yet consulted** by any prediction path — a pure data-collection phase, functionally invisible, to build real correction volume before any prediction behavior changes (mirrors the shadow-mode pattern used by the sibling OCR specs).
2. Ship the merchant-alias write-back next — lowest risk, extends an already-shipped, already-validated table and access pattern. Enable once shadow-mode data confirms the capture pipeline is reliable.
3. Ship category preference next — per-user, self-contained blast radius, includes the free historical backfill.
4. Ship OCR-misread-pattern aggregation and its consumption last — highest complexity (the abstraction/anonymization step, cross-user aggregation), least existing precedent to build on, and the piece the resolved privacy decision most directly constrains. Ship only once the first three phases have validated the capture → store → consult pattern end to end on lower-risk data.
5. Each phase behind its own flag, independently revertible. The corrections log itself is purely additive and never needs rollback even if a consuming phase is disabled — disabling consumption just stops learned signals from influencing predictions, with zero data loss and zero effect on the existing heuristic/LLM pipeline's baseline behavior.
