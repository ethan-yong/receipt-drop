# Feature: Illumination Normalization & Shadow Correction for OCR Preprocessing

## Overview

A new, gated preprocessing stage in `services/ocr-api` that detects and corrects uneven lighting — shadows cast by hands/objects, ambient gradients, glossy-paper hotspots, dark vignetting near frame edges — in receipt photos before they reach Tesseract. It extends the pipeline `services/ocr-api/ocr_api/preprocessing.py` already implements (decode → optional perspective correct → deskew → upscale → grayscale → contrast-gated CLAHE → optional sharpen → Tesseract → adaptive-binarize retry), inserting one new heuristically-gated step rather than replacing anything. It targets the specific real-world capture conditions this app's users hit constantly: a receipt held in one hand, photographed indoors under a single overhead light or outdoors in dappled shade, at a cafe or restaurant table.

## Problem Statement

The current pipeline has no step that corrects large-scale spatial lighting gradients. `enhance_contrast()` (CLAHE) is gated on global grayscale std-dev (`_is_low_contrast()`) — it fires when an image's overall dark-text-vs-light-background contrast is low, but a shadow across half a receipt doesn't necessarily lower *global* contrast (the shadowed half can still have plenty of dark-text-on-darker-background local contrast); CLAHE's tiled local-contrast enhancement doesn't flatten a directional brightness gradient, and can amplify a shadow's edge into a false document boundary. Tesseract's own internal thresholding assumes a roughly uniform background — a lighting gradient makes it threshold one region of a receipt into the wrong class (background swallowing faint text, or text merging with a dark background band), dropping words or splitting lines.

The pipeline currently only reacts to this after the fact: `ocr_engine.run_ocr_detailed()` retries with `shadow_binarize()` (an adaptive threshold explicitly commented as targeting "e.g. phone-flash shadows") when the first Tesseract pass scores below 0.4 calibrated confidence. This is a real, working mitigation, but it's reactive and costly — it's a second full Tesseract pass, budget-gated at `_RETRY_TIME_BUDGET_SECONDS` (20s) specifically because of a documented production incident where a slow, low-confidence plain pass (51s) was followed by a retry (70s) that scored *worse* — 122s wasted for zero benefit. A preventive fix that corrects the lighting gradient before the first Tesseract pass can raise first-pass confidence enough that fewer requests hit the low-confidence retry branch at all, for the specific subset of low-confidence cases actually caused by lighting rather than blur, low resolution, or genuine print fade.

## Goals

- Detect when an image has spatially uneven illumination (shadow gradient, hotspot, vignetting) as distinct from the existing "globally low contrast" signal `_is_low_contrast()` already checks.
- Correct detected unevenness by flattening the large-scale brightness gradient while preserving fine text-stroke detail, using only classical CV operations already available via the existing OpenCV/numpy dependency (no new library).
- Run only when correction is likely to help; leave already-evenly-lit images byte-for-byte or near-byte-for-byte unmodified.
- Reduce (not eliminate) the frequency with which the existing low-confidence binarize-retry path triggers, for the lighting-caused subset of low-confidence first passes — without touching that retry path's own logic, threshold, or time budget.
- Extend `preprocessing.py` incrementally, following the exact env-flag / heuristic-gate / backward-compatible-`/ocr`-response conventions the 2026-07-21 preprocessing upgrade plan established for this same file.

## Non-Goals

- Not a pipeline rewrite or a change to the OCR engine (stays Tesseract/`pytesseract`).
- Not a change to perspective correction, deskewing, or upscaling — those stages are untouched, both in behavior and in their position in `preprocess()`.
- Not a trained/ML-based shadow-removal model. The rest of this pipeline has zero ML preprocessing dependencies (it's classical CV feeding a classical OCR engine, with the LLM step happening only after OCR text exists) — this feature keeps that property.
- Not a client-side (Flutter) capture-time correction or live camera preview enhancement. Scope is entirely server-side, `services/ocr-api`, matching where every other preprocessing stage lives.
- Not a change to `_RETRY_TIME_BUDGET_SECONDS`, the 0.4 low-confidence retry threshold, or `shadow_binarize()`'s own logic — those stay exactly as they are; this is a new, independent, earlier-pipeline stage.
- Not white-balance or color-cast correction. This stage operates after grayscale conversion (see Technical Design) — color information is already gone by the time it would run, and shadow/lighting problems are fundamentally luminance problems as far as Tesseract is concerned.
- Not a fix for multi-document-in-one-frame captures — no new segmentation logic; inherits the existing single-largest-quad assumption from `detect_document_corners()`.
- Not a general low-light / underexposure fix. Severe global underexposure (the whole image is dark, not just part of it) is a different problem from a spatial gradient and is explicitly out of scope here — see Edge Cases and Decision Logic for how this stage avoids overreaching into that case.

## Proposed Solution

Add one new gated stage to `preprocess()`, inserted between grayscale conversion and the existing contrast-gated CLAHE step. The stage has two parts:

1. **A cheap detector** that quantifies spatial illumination unevenness — distinct from `_is_low_contrast()`'s *global* std-dev check — by comparing brightness across a coarse grid of regions over the image. A large spread between regions (relative to the image's own overall brightness/contrast) indicates a gradient, shadow, or hotspot; a small spread indicates already-even lighting.
2. **A correction routine**, run only when the detector fires, that estimates the image's background illumination via a large-kernel blur/morphological-closing pass (large enough to bridge over individual text strokes but track the broader lighting gradient), then divides the original image by that background estimate and rescales — a standard "shading correction" / flat-field-normalization technique that flattens gradients while leaving high-frequency content (text edges) comparatively intact, because the background estimate is barely perturbed by thin, sparse dark strokes on a mostly-light receipt.

Because correction can occasionally do more harm than good (over-brightening an already-fine region, blowing out highlights, washing out already-faint thermal-print text), the stage applies a small set of **pre-Tesseract pixel-statistics guards** after correction and reverts to the uncorrected image if they fail — see Decision Logic. This deliberately avoids the alternative of validating via a second Tesseract pass (an OCR-confidence-based A/B), which would risk reintroducing the same class of latency problem the existing 122s incident already forced a budget guard around.

The existing CLAHE gate (`_is_low_contrast()`) is re-evaluated *after* this new stage, against whatever image the new stage produced (corrected or reverted-to-original) — not against the raw grayscale image as today. This is a real, intentional reordering: illumination correction changes the image's global contrast profile, so CLAHE's gate should see the corrected image's actual contrast, not the pre-correction one.

## User Experience

This is a backend pipeline change with no new UI and no new user-facing states — the user-visible effect is indirect, through existing surfaces:

- **Golden path**: a user photographs a receipt with a visible shadow (their hand, phone, an overhead light). Today this may score low enough on the first Tesseract pass to trigger the binarize retry (adding latency) or, in the worst case, still fail to extract merchant/amount and land the receipt in the existing `needs_review` queue (`pipeline_status='needs_review'`, `docs/system/decisions.md`'s 2026-07-05 entry). With this feature working as intended, the same photo has its lighting flattened before the first Tesseract pass; the user sees no new screen or indicator, but the receipt is more likely to auto-save with a correct amount/merchant on the first pass, and less likely to need the (already-existing) review-queue confirm step.
- **Already-clean capture**: a receipt photographed under even light is unaffected — the detector doesn't fire, the image passes through unchanged, and behavior is identical to today.
- **Over-correction (guard-rejected)**: if correction is attempted but the pixel-statistics guards judge it degraded the image, the stage silently reverts to the pre-correction image and the rest of the pipeline proceeds exactly as if the new stage weren't gated on. No user-visible difference from today's behavior in this case — the fallback is invisible by design, same as `shadow_binarize()`'s existing internal OTSU fallback when its adaptive output is degenerate.
- **Failure inside the new stage**: an unexpected exception in the detector or correction routine must not fail the `/ocr` request. It should be caught, logged, and treated as "skip this stage" — falling through to the uncorrected image — matching this codebase's existing pattern of degrading gracefully rather than failing outright (e.g. the LLM understanding step's `understanding: null` / `understanding_error` degrade-not-fail design from the 2026-07-10 decision).
- **Feedback mechanism**: none new and user-facing. The only feedback loop is internal/operational: server logs (each stage in `preprocessing.py` already logs its decision at INFO) and the existing opt-in `PREPROCESS_DEBUG` stage-PNG dumps, both consumed by whoever is tuning the pipeline, not by end users.

## System Impact

- **Backend services**: `services/ocr-api` only. New functions and a new wired-in stage inside `ocr_api/preprocessing.py`. `ocr_api/main.py`'s `POST /ocr` route is unaffected — it still calls `preprocess()` then `run_ocr_detailed()` with the same signatures and the same response schema. `ocr_api/ocr_engine.py` needs no signature change; only its *behavioral* interaction with `preprocess()`'s output changes (see Decision Logic).
- **Client application**: none. `/ocr`'s response schema is unchanged, so `lib/features/share/ocr_pipeline_io.dart`, `receipt_parse_pipeline.dart`, and everything downstream require zero changes, matching the same guarantee the 2026-07-21 plan made for its own changes.
- **Database/storage**: none. No schema change, no new persisted field.
- **AI/ML pipeline**: Tesseract's own configuration (`_config()`, PSM/language) is untouched — only the image handed to it changes. The synchronous LLM receipt-understanding step (`call_receipt_understanding`, downstream of OCR text) is affected only indirectly, insofar as cleaner OCR text is a better input to it — no direct code interaction.
- **Infrastructure**: none. No new dependency (stays within the existing `opencv-python`/`numpy` toolset already used by every other stage in this file), no new deploy step, no new secret.
- **External integrations**: none.

## Technical Design

**Where this runs in the pipeline.** `preprocess()`'s stage order becomes: decode → optional perspective correct → deskew → upscale → grayscale → **illumination detect+correct (new)** → contrast-gated CLAHE (re-evaluated against the new stage's output) → optional sharpen → return, ready for Tesseract. It runs after grayscale (this stage only needs luminance, and every downstream stage already operates in grayscale) and before CLAHE (CLAHE's local-contrast enhancement should operate on an already-lighting-flattened image, not fight a raw gradient — matches the general document-preprocessing convention of "global correction before local enhancement").

**Detection component.** A grid-based unevenness score: partition the grayscale image into a coarse block grid, compute each block's mean brightness, and measure the spread across blocks (e.g. max-min range, or block-mean std-dev) relative to the image's overall statistics. This is a materially different signal from `_is_low_contrast()`'s single global std-dev — an image can be globally high-contrast (crisp dark text on light background) while still having one shadowed corner, and vice versa; the two gates answer different questions and both are needed. The detection cost is a handful of block-mean computations over an already-decoded-and-resident array — negligible next to the correction step itself.

**Correction component.** Background/illumination-map estimation via a strong low-pass operation (a large-kernel Gaussian blur or a morphological closing with a large structuring element) sized so it bridges across individual text strokes (which are thin and sparse on a receipt) but still tracks the broader spatial gradient. The original image is then divided by this estimated background (with the result rescaled to a full 0–255 range around a target mid-brightness), which is the standard flat-field/shading-correction technique: regions the background-estimate reports as darker (shadowed) get pulled brighter relative to regions it reports as lighter, while the fine high-frequency detail the background estimate never captured (the text itself) survives comparatively intact.

**Quality guards (pre-Tesseract, not OCR-confidence-based).** After correction, before committing to it, run two cheap statistical checks against the corrected image compared to the pre-correction one:
- A **clipping guard**: division normalization can blow out already-bright regions into full saturation. If the corrected image has materially more pixels newly at the 0/255 extremes than the original did, treat correction as having discarded information rather than recovered it.
- A **bimodality guard**: receipts want a histogram Tesseract's internal Otsu thresholding can cleanly split into "text" and "background" populations. Otsu's between-class variance (cheaply available from the histogram, or from OpenCV's threshold call) is a proxy for how bimodal/separable the image's brightness distribution is. If this drops materially after correction, the correction likely washed out text-vs-background separation (a real risk on already-faint thermal or faded prints) rather than improving it.

If either guard fails, the stage reverts to the pre-correction (post-grayscale) image and logs that it did so. This keeps the entire decision pre-Tesseract and cheap — explicitly not a second OCR pass — which matters because the existing retry path already owns the one place in this pipeline where a second full Tesseract pass is considered acceptable, and that place has a documented, hard-won latency budget (`_RETRY_TIME_BUDGET_SECONDS`) this feature must not duplicate or endanger.

**Interaction with the existing retry path.** `ocr_engine.shadow_binarize()` keeps its exact signature and logic, untouched. Its adaptive-threshold retry now operates on an image that has (when this stage fired and wasn't reverted) already had its gross lighting gradient flattened — expected to reduce, not eliminate, both how often the retry triggers and how often `shadow_binarize()`'s own degenerate-output-to-OTSU fallback engages. No code coupling is introduced; this is a behavioral, not structural, interaction, and should be validated empirically (see Testing Strategy) rather than assumed.

**Flags**, following this file's existing convention (every stage is env-tunable, defaults chosen per stage rather than uniformly):
- A master switch analogous to `PREPROCESS_CLAHE` — heuristic-gated on by default (the detector itself is the safety net against touching already-clean images), with an explicit `"0"` value to hard-disable regardless of the detector.
- A tuning threshold for the detector's unevenness score, analogous to `PREPROCESS_CLAHE_CONTRAST_THRESHOLD`.
- Tuning knobs for the correction routine's kernel size and target rescale brightness, analogous to `PREPROCESS_SHARPEN_AMOUNT`/`PREPROCESS_SHARPEN_SIGMA`.
- The existing `PREPROCESS_DEBUG` stage-dump mechanism gains new stage names for this feature (the background estimate, the corrected-before-guard-check image, and the final chosen image), so a guard revert is inspectable after the fact.

Exact env var names, default numeric thresholds, and kernel-size formulas are implementation details to be chosen and tuned during implementation (see Implementation Guidance and Decision Logic) — no real threshold is asserted here as final, consistent with how every other tunable constant in this file is explicitly marked "tune against real fixtures" in its own comment.

## Decision Logic

- **When the detector runs**: always, on every request, unless the master flag is explicitly set to hard-disable (`"0"`) — mirrors `PREPROCESS_CLAHE`'s pattern exactly. The detector itself is cheap enough to always compute.
- **When correction runs**: only if the master flag is not hard-disabled **and** the detector's unevenness score exceeds its threshold. Below threshold, the image passes through unmodified — no wasted correction work, and no risk to already-clean images, directly satisfying "avoid modifying already-clean images unnecessarily."
- **When correction is kept vs. reverted**: after running, both quality guards (clipping, bimodality) must pass for the corrected image to be kept. If either fails, revert to the pre-correction (post-grayscale) image and proceed as if correction had not fired at all.
- **When the stage is skipped due to a different problem entirely**: if the image's overall brightness is below a floor (i.e., the image is globally very dark, not just unevenly lit — see Edge Cases), skip correction even if the detector's grid-variance score would otherwise fire. A globally dark image dividing by an equally-dark background estimate amplifies noise rather than fixing a gradient; this is a different failure mode (global underexposure) explicitly out of scope for this feature, left to the existing CLAHE/retry path exactly as it's handled today.
- **Ordering relative to CLAHE**: CLAHE's own `_is_low_contrast()` gate is evaluated against this stage's output (corrected-and-kept, or original-because-skipped-or-reverted) — never against the pre-illumination-stage grayscale image. This is a real behavioral change to an already-shipped stage's input, not just an addition (see Implementation Guidance's risk callout).
- **Ordering relative to sharpen**: unchanged — sharpen still runs last, opt-in, after CLAHE, operating on whatever image reaches it.
- **On internal exception**: any unhandled exception inside the detector or correction routine is caught at the stage boundary, logged, and treated as "skip this stage, use the pre-stage image" — never propagated up to fail the `/ocr` request.
- **Interaction with the low-confidence retry threshold** (`ocr_engine._LOW_CONFIDENCE_RETRY_THRESHOLD` = 0.4) and **the retry time budget** (`_RETRY_TIME_BUDGET_SECONDS` = 20.0): both stay exactly as-is. This feature does not read, write, or reason about Tesseract confidence at all — it operates entirely before Tesseract's first pass and has no visibility into (and no business influencing) the retry decision beyond the indirect effect of possibly raising the first pass's own confidence.

## Edge Cases

- **Receipt with a colored (non-white) background, evenly lit** (e.g. a yellow thermal roll, a colored promotional receipt): grayscale conversion already happened upstream of this stage, so it's operating on luminance only. An evenly-lit colored receipt has low grid-variance in luminance terms and the detector correctly does not fire — no different from a white receipt in this regard.
- **Receipt with a colored background, unevenly lit**: correction still operates correctly since the problem (a luminance gradient) is exactly what this stage targets, regardless of the original hue — Tesseract only ever sees grayscale input from this pipeline anyway.
- **Thermal receipts (low ink density, faint print)**: at risk of the bimodality guard reverting correction, since a receipt with already-marginal text/background separation is the case most likely to have that separation *worsen* under aggressive background estimation. This is the guard's intended job — expect a nontrivial revert rate on this receipt class, not a bug.
- **Faded receipts**: same risk profile and same mitigation as thermal receipts above.
- **Glossy paper reflections / bright hotspots**: division normalization directly targets this case (a locally bright background estimate gets divided back down) — expected to be one of the clearer wins for this feature. A genuinely *saturated* reflection (a region that clipped to pure white in-camera, with zero recoverable text detail) cannot be recovered by any postprocessing — normalization can rebalance gradients but not invent missing information; this is a hard limitation, not a defect.
- **Very dark / severely underexposed images**: explicitly guarded against via the brightness-floor check in Decision Logic — this is a global-exposure problem, not a spatial-gradient problem, and forcing this stage to "fix" it by dividing by an equally-dark background estimate would amplify sensor noise. Left to fall through to the existing CLAHE/retry handling unchanged.
- **Multiple receipts in one photographed frame**: no dedicated handling — inherited limitation from `detect_document_corners()`'s existing single-largest-quad assumption. The detector's grid-variance heuristic could register the boundary between two documents (or a document and background surface) as a "gradient," but this is not meaningfully different from how the rest of the pipeline already assumes a single document per image; not a regression this feature introduces.
- **Correction routine throws an exception on malformed/edge-case input** (e.g. a degenerate near-zero-size image slipping past `decode_image`): caught and treated as "skip this stage," per Decision Logic — must never propagate to fail `/ocr`.
- **A request explicitly forcing `PREPROCESS_ADAPTIVE_BINARIZE=1`** (the existing forced-binarize test/debug path in `ocr_engine.run_ocr_detailed`): that path calls `shadow_binarize()` directly on whatever `preprocess()` returned, so this stage's output (corrected or not) still feeds into it exactly as it would feed into a normal first pass — no special-casing needed, but worth a regression test given it's an existing alternate code path.
- **`PREPROCESS_DEBUG=1` combined with a guard revert**: the debug dump set must include the rejected corrected image (not just the final chosen one), or a revert becomes unverifiable after the fact during tuning.

## Performance Considerations

- **Detection cost**: negligible — a handful of block-mean computations over an already-resident grayscale array, cheaper than the existing `_is_low_contrast()` global std-dev call it sits alongside.
- **Correction cost (when triggered)**: the dominant new cost. A large-kernel blur/morphological-closing pass over the full working-resolution image (post-`upscale_for_ocr`, so potentially a ~2500px-wide image per `_MIN_OCR_WIDTH`'s existing default) is measurably more expensive than CLAHE's tiled histogram equalization or the sharpen stage's small-kernel unsharp mask. This must be benchmarked, not assumed, against the pipeline's overall latency ceiling — the existing 20s retry-skip budget and the documented ~90s ocr-proxy/Cloudflare-tunnel round-trip ceiling (`ocr_engine.py`'s `_RETRY_TIME_BUDGET_SECONDS` comment) are the concrete constraints this stage's cost must respect, with headroom, since it now runs unconditionally-checked (if not unconditionally-corrected) on every request.
- **Ordering cost tradeoff**: running after `upscale_for_ocr` (as proposed) means the expensive part of this stage operates on the larger, upscaled image rather than the original — more precise (more pixels to distinguish a real gradient from noise) but more expensive than correcting pre-upscale would be. This is inherited from the existing pipeline's already-established stage order (upscale before grayscale), not a new choice this feature is making, but it's the reason this stage's cost is nontrivial rather than trivial.
- **Memory**: one or two additional float32/uint8 intermediate buffers at working resolution (the background estimate, the corrected candidate before the guard check) — bounded and request-scoped, the same pattern every existing stage already follows (deskew, upscale, grayscale, and CLAHE each already allocate a fresh array).
- **Batch processing**: `bin/process_receipts.dart` / `scripts/process_receipts.ps1` call `/ocr` once per file, sequentially — this feature adds the same per-request cost to each call with no new batching-specific concern.
- **Mobile/on-device cost**: not applicable — this entire feature lives in `services/ocr-api`, server-side; the Flutter client never runs any of this code, matching the rest of the preprocessing pipeline.
- **Network cost**: none — no new external call, purely local CPU-bound image processing inside the existing `/ocr` request.

## Security Considerations

- **Authentication**: unchanged. This stage runs inside the same `X-OCR-Secret`-gated `/ocr` endpoint every other preprocessing stage already runs inside; no new auth surface.
- **Data privacy**: no new data persisted. `PREPROCESS_DEBUG` dumps (already opt-in, already gitignored per the prior plan's checklist item) simply gain a couple of new stage names — no change to the existing privacy posture of that mechanism.
- **Abuse / DoS surface**: a crafted image engineered to maximize the detector's positive rate could force the more expensive correction path on every request against a given deployment. This risk already exists identically today for `PREPROCESS_PERSPECTIVE`'s Canny/contour detection and for CLAHE's gated path, and `/ocr` is not public-internet-exposed — it's ClusterIP-only behind Cloudflare Access plus the shared secret, per the 2026-07-16 security-hardening decision. No new mitigation is warranted beyond what's already in place; this is noted rather than treated as a gap.

## Tradeoffs

- **Background-estimate-and-divide vs. Retinex-based illumination correction**: Retinex (single- or multi-scale) has stronger theoretical grounding for separating illumination from reflectance, but costs more (multiple Gaussian scales, log-domain operations) and adds more tuning surface. Rejected for a first pass in favor of the simpler technique, consistent with this codebase's repeated "measure the simple thing before adding complexity" pattern (CLAHE's contrast gate, sharpen's default-off) — worth revisiting only if the simple approach's measured batch results (see Testing Strategy) prove insufficient.
- **Background-estimate-and-divide vs. homomorphic (frequency-domain) filtering**: theoretically clean separation of illumination/reflectance via log + FFT high-pass, but introduces an FFT dependency and ringing artifacts near text edges. Rejected for the same "avoid complexity without measured justification" reason.
- **Pixel-statistics guards vs. an OCR-confidence-based quality check**: the existing retry path already demonstrates what a confidence-based A/B costs — a second full Tesseract pass, budget-gated because of a documented 122s-wasted incident. Stacking a *second* such mechanism onto this new stage (running Tesseract, checking confidence, reverting) would risk compounding exactly that failure mode. Pixel-statistics guards keep this stage's entire decision pre-Tesseract and cheap, at the cost of being a weaker (proxy, not ground-truth) quality signal — accepted as the right tradeoff given the latency constraint is a hard, previously-learned lesson in this codebase.
- **Operating in grayscale vs. correcting the color image pre-grayscale-conversion**: correcting before grayscale conversion would in principle allow per-channel color-cast correction, but every downstream stage (CLAHE, sharpen, Tesseract itself) already operates in grayscale, and moving grayscale conversion later in the pipeline would touch more of an already-shipped, tested pipeline than this feature needs. Rejected — shadow/lighting problems are fundamentally luminance problems from Tesseract's point of view regardless.
- **Heuristic-gated-on-by-default vs. opt-in-off-by-default**: the immediately-preceding plan chose opt-in-off for sharpen (an enhancement with no clean self-gating signal) but heuristic-gated-on for CLAHE (which has a cheap, reliable "is this even needed" check). This feature has an equally cheap, reliable detector, so the recommendation follows CLAHE's precedent rather than sharpen's — but this is explicitly a recommendation for Implementation Guidance/Rollout to revisit if real-fixture tuning suggests the detector's false-positive rate is too high to trust as a default-on gate.

## Implementation Guidance

**Suggested order of work**, mirroring how `services/ocr-api/ocr_api/preprocessing.py`'s existing stages were each built and tested in isolation before wiring:

1. Add the grid-based illumination-unevenness detector as a standalone function; unit-test it against new synthetic fixtures (extend `services/ocr-api/tests/conftest.py` with a shadow-gradient fixture — e.g. a directional brightness gradient or a soft dark ellipse blended over one corner of the existing `clean_receipt_image` fixture, following the same construction pattern already used for `skewed_low_contrast_image`/`low_light_receipt_image`) and confirm it does *not* fire on the existing clean fixture (no false positive on already-good input).
2. Add the background-estimation + division-normalization correction function in isolation (not yet wired into `preprocess()`), with tests asserting it measurably flattens the synthetic gradient fixture (e.g. re-running the detector's own grid-variance metric against the corrected output and asserting it dropped).
3. Add the two pixel-statistics quality guards (clipping, bimodality) with tests that include at least one deliberately-pathological case (e.g. an already-flat or already-faded fixture fed through correction directly) confirming the guard reverts rather than lets a degraded image through.
4. Wire the full stage into `preprocess()` behind its new env flag(s), in the position between grayscale and the (now-reordered) CLAHE gate.
5. Add one route-level regression test in `services/ocr-api/tests/test_main.py` confirming `/ocr`'s response schema is unchanged with the new flag(s) set — mirroring the exact final checklist item of the 2026-07-21 plan this one extends.
6. Run `scripts/process_receipts.ps1` against a folder of real receipt photos with genuine shadows/uneven lighting (not just synthetic fixtures) to tune the new threshold/kernel constants before considering the feature done — every existing tunable constant in this file (the CLAHE std-dev threshold, the sharpen amount/sigma, the document-area ratios, `MIN_OCR_WIDTH` itself) was tuned this way and carries an inline comment saying so; this feature's constants should get the same treatment and the same comment discipline, not ship as asserted-final defaults.

**Files to inspect first**: `services/ocr-api/ocr_api/preprocessing.py` (where every new function lands — keep the existing flat-module decision, do not split into a package, per the prior plan's explicit module-structure decision, which still applies and wasn't reversed); `services/ocr-api/ocr_api/ocr_engine.py` (read-only reference to confirm no signature changes are needed and `shadow_binarize()` stays untouched); `services/ocr-api/tests/conftest.py` and `tests/test_preprocessing.py` (fixture and test-naming conventions to extend, not reinvent); `docs/plans/2026-07-21-ocr-preprocessing-pipeline-upgrade.md` (the immediately-preceding plan — same file, same conventions, same "env-flag/heuristic-gate, backward-compatible response" shape this spec deliberately continues).

**Risks**:
- `_RETRY_TIME_BUDGET_SECONDS` / the documented 122s incident is the single most load-bearing invariant near this code. Any implementation choice that, even indirectly, ends up running Tesseract twice as part of *this* stage's own quality check would be reintroducing exactly the problem that constant exists to prevent — the pixel-statistics-guard design in this spec exists specifically to avoid that path; don't drift toward an OCR-confidence-based guard during implementation without deliberately revisiting this tradeoff.
- Shipping default threshold/kernel constants without real-fixture tuning carries the same risk already explicitly flagged for the CLAHE contrast threshold and document-area ratios in `docs/system/decisions.md`'s 2026-07-22 entry ("pending batch tuning") — don't let this feature's constants quietly become "final" without the same batch-run validation step.
- The CLAHE-gate reordering (its `_is_low_contrast()` check now evaluates the *post*-illumination-stage image, not the raw grayscale image) is a behavioral change to an already-shipped, already-tested stage, not just an addition alongside it. The existing CLAHE-gate tests in `test_preprocessing.py` should be re-examined against this reordering, not just left as-is while new tests are appended around them.

## Testing Strategy

- **Unit tests** (`services/ocr-api/tests/test_preprocessing.py`): detector correctly flags a synthetic shadow-gradient fixture and correctly does not flag `clean_receipt_image`; correction measurably reduces the detector's own unevenness metric on the gradient fixture; the clipping guard rejects a case engineered to over-saturate; the bimodality guard rejects a case engineered to wash out text/background separation (e.g. run correction against an already-faded/low-density fixture and assert it reverts).
- **Route-level regression test** (`services/ocr-api/tests/test_main.py`): `/ocr`'s response schema is unchanged with the new flag(s) set, following the exact pattern the prior plan's own final test item established.
- **Before/after real-world comparison**: use the existing `scripts/process_receipts.ps1` / `bin/process_receipts.dart` batch tool against a folder of real receipt photos with genuine shadows/uneven light (the same evaluation mechanism already used and documented inline to tune `MIN_OCR_WIDTH`, with its own recorded before/after confidence delta) — run once with the feature hard-disabled and once with it enabled, and diff results field-by-field rather than inventing a new evaluation harness.
- **Accuracy metrics**: calibrated OCR confidence (`_calibrate_confidence`'s existing output, already logged per pass); recognized word/line count (a genuine shadow fix should recover previously-missing text, which shows up as more words, not just a confidence nudge); with `-E2e`, downstream parse success (amount/merchant/line-items extracted correctly or not), matching the batch tool's existing E2E mode.
- **Retry-path interaction check**: as part of the same batch run, track how often the low-confidence binarize retry actually triggers with the feature on vs. off — this is the concrete, measurable version of this spec's claim that first-pass confidence improves for lighting-caused cases, and should be reported alongside the raw confidence numbers rather than assumed.
- **Failure-path visibility**: confirm (via logs, and via `PREPROCESS_DEBUG` dumps including the rejected-corrected-image stage) that a guard revert is actually observable during tuning — an invisible silent fallback can't be tuned or debugged later.
- **No new UI/device testing** is needed — this is a headless, server-side-only change with no client-visible surface, unlike this repo's UI-facing features (map, share flow) that require manual device verification.

## Rollout Plan

- Ships entirely behind the new env flag(s), following the exact posture the 2026-07-21 upgrade used for its own new stages: deployed k8s behavior does not change on redeploy unless a flag is explicitly set.
- Because the recommended default (heuristic-gated-on, matching CLAHE's precedent — see Tradeoffs) is a *default-behavior* change unlike the previous plan's default-off sharpen stage, recommend a staged flip rather than shipping default-on immediately: (1) deploy with the feature's master flag hard-disabled (`"0"`) — zero behavior change; (2) run `scripts/process_receipts.ps1` against the real `receipts/` fixture folder to tune thresholds/kernel size and confirm no regression on already-clean receipts; (3) flip the flag on (or remove the override, letting the heuristic-gated default take effect) via the existing `deploy.ps1` flow.
- No schema or migration involved — this is a stateless service config change to `services/ocr-api` only. Rollback is re-setting the env var to `"0"` and redeploying, identical in mechanism to disabling `PREPROCESS_CLAHE` or `PREPROCESS_SHARPEN` today.
- No feature-flag system beyond this repo's existing env-var convention exists in `services/ocr-api` (no GrowthBook/LaunchDarkly-style gate anywhere in this service) — env-var gating is the correct and only available mechanism, consistent with every other stage in this pipeline.
