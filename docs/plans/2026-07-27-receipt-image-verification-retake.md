# Feature: Receipt Image Verification & Retake

## Overview
Adds a lightweight verification layer to the post-scan experience: users can see the receipt photo they captured alongside the extracted transaction data, open it full-screen to check faint or ambiguous text, and retake/reprocess a scan in place when the capture or OCR result is unsatisfying. It closes a real gap: the app already durably stores every receipt photo (Supabase Storage + `receipt_artifacts`), but no screen actually surfaces it to the user, and there is no recovery path short of deleting the whole transaction.

## Problem Statement
`transaction_detail_screen.dart:233` reserves a 200×200 slot for `ReceiptThumbnail` but calls it with zero arguments (`ReceiptThumbnail(size: 200, radius: ...)`), so it always falls through to the generic placeholder icon — the user's own photo is never shown on the one screen built to display it (confirmed by reading the file directly). `receipt_confirm_sheet.dart` never renders it either. Meanwhile every capture already writes a durable, private, RLS-scoped artifact (`OutboxArtifacts` → `receipt_artifacts` + `receipts` Storage bucket) — the data exists, it's just never surfaced. Combined with real-world receipt quality issues (thermal fade, glare, skew, folds) and no existing way to fix a bad capture except deleting the transaction outright, users have no way to build confidence that OCR read their receipt correctly, and no graceful recovery when it didn't.

## Goals
- Show the actual captured receipt photo next to extracted transaction data (not instead of it).
- Let users open the photo full-screen and zoom, to check faint/small print against extracted fields.
- Let users retake a photo and reprocess an existing transaction without deleting/recreating it or re-entering data by hand.
- Surface a quiet, non-alarming quality signal (reusing the app's existing confidence/needs-review logic) that nudges — never forces — a review or retake.

## Non-Goals
- No new "enhanced/preprocessed" image pipeline. `services/ocr-api`'s preprocessing (deskew, upscale, grayscale) already runs in-memory and is discarded (`PREPROCESS_DEBUG` off by default); this feature displays only the original captured photo. Explicit assumption — flagging in case product later wants a human-legible enhanced variant.
- No change to OCR/LLM parsing logic itself — only when/how it's invoked and how results reconcile into an already-saved transaction.
- No multi-photo-per-receipt / scan-attempt history. Confirmed with the user: retake uses **replace** semantics — one current image per transaction, old artifact deleted on confirmed retake, not versioned.
- No change to `receipt_card.dart`'s home carousel — it deliberately excludes the user's photo in favor of category illustration art (explicit comment in that file); this feature must not alter that.
- No new abuse-control/rate-limiting work on the OCR call path — retake reuses the exact same call as first capture; flagged as an assumption that existing controls already cover repeat invocation (see Security Considerations).

## Proposed Solution
Fix the dead UI wiring first: the transaction detail screen resolves and displays the real photo (local file if present on-device, else a lazily-fetched signed Storage URL, since the `receipts` bucket is private) instead of an unwired placeholder. Tapping it opens a new full-screen zoomable viewer, structurally modeled on `place_picker_screen.dart`'s existing fullscreen-route/overlay-bar pattern (`InteractiveViewer` around the image, top-bar close, bottom-bar Retake — no new dependency). Retake reuses the existing capture menu and `ReceiptScanProcessingScreen` OCR pipeline, then routes results through `ReceiptConfirmSheet` in a new "edit existing transaction" mode rather than silently overwriting anything — the user always explicitly confirms before a rescan takes effect. On confirm, a new repository method deletes the old artifact (local file + Storage object + row) and inserts a fresh one for the same transaction, updates the transaction's OCR-derived fields, and lets the existing sync/enrich pipeline run unchanged. A quiet quality-nudge tag reuses the app's already-computed `pipeline_status`/confidence signal — no new scoring logic.

## User Experience
- **Golden path (view + verify, healthy confidence)**: open transaction detail → real receipt thumbnail shown next to extracted fields (not full-width — complements, doesn't dominate) → tap thumbnail → full-screen pinch/pan viewer opens with close (X) and Retake → user checks faint text against extracted values → closes, nothing changes.
- **Low-confidence nudge**: when `pipeline_status == 'needs_review'` (existing signal, no new threshold), a small non-blocking tag appears near the thumbnail (e.g. "check this scan") → tapping it opens the same full-screen viewer, one tap from Retake. High-confidence transactions show no tag at all — no interruption to the golden path.
- **Retake path**: from the viewer's Retake action → same capture menu as first capture (camera/gallery) → `ReceiptScanProcessingScreen` runs OCR against the new image (its existing retry-on-failure UI already covers OCR-call failure) → on success, `ReceiptConfirmSheet` opens pre-filled with the NEW extracted merchant/amount/category/line items and the NEW photo → user edits/confirms → Save commits (old artifact deleted, new one written, transaction fields updated) → back on detail screen showing the new photo and fields.
- **Cancel mid-retake**: backing out of the processing screen or the confirm sheet without saving discards the newly captured local file and writes nothing — original artifact and transaction are untouched, mirroring the existing `discardDraft()` behavior for first-time capture.
- **Missing local file** (reinstall, new device, cleared app storage): thumbnail/viewer fall back to a signed Storage URL; if that's also unavailable (never synced, e.g. created fully offline before a reset), show the existing placeholder icon with a short explanatory label ("Photo not available on this device yet") instead of a blank or broken image.

## System Impact
- **Client application** (primary surface): `transaction_detail_screen.dart` (wire thumbnail, add nudge tag, add Retake entry point), new full-screen viewer widget, `receipt_confirm_sheet.dart` (new edit-existing-transaction mode), `transaction_repository_native.dart` / `_web.dart` (new `resolveDisplayImage` + `replaceArtifactAndReprocess` methods), `transaction_view.dart` (new nullable field carrying the artifact's remote storage path).
- **Backend services**: Supabase Storage (one delete + one insert per confirmed retake, existing `receipts` bucket/RLS reused as-is); `enrich-transaction` re-runs naturally through the existing sync path when merchant text changes — no changes to that function itself.
- **Database/storage**: no migration. The chosen replace semantics preserve the existing implicit "one artifact per transaction" invariant that `SyncWorker.run` already relies on (`getSingleOrNull()` on `outbox_artifacts` by `transactionId` — this would throw if a second row ever existed, which is exactly why replace-not-version was chosen).
- **AI/ML pipeline**: no logic change — OCR/LLM is simply invoked again, same as any capture, against a new image for an existing transaction id.
- Infrastructure / external integrations: none beyond what's already used.

## Technical Design
- **Display resolution**: extend `TransactionView` with a nullable `remoteStoragePath` (mirrors `receipt_artifacts.storage_path`, already tracked locally on `OutboxArtifacts.storagePath` but not currently surfaced onto the view model). Add `TransactionRepository.resolveDisplayImage(transactionId)`: if the file at `localThumbnailPath` still exists on disk, use it directly (fast, fully offline); else if `remoteStoragePath` is set, request a short-lived signed URL from Supabase Storage for it; else return "unavailable." Wire this into `transaction_detail_screen.dart`'s existing `ReceiptThumbnail(...)` call (currently passed no arguments at all) and reuse `ReceiptThumbnail`'s existing `imageUrl`/`localPath`/loading/placeholder states as-is.
- **Full-screen viewer**: new screen (e.g. `lib/features/tx_detail/receipt_image_viewer_screen.dart`), pushed the same way `PlacePickerScreen` is (`Navigator.of(context, rootNavigator: true).push(MaterialPageRoute(fullscreenDialog: true, ...))`) — same Stack/Positioned.fill/overlay-bar shape, no shared code, just the same proven structural pattern. Body is `InteractiveViewer` (Flutter SDK, no new package) around the same resolved image source as the thumbnail.
- **Retake orchestration**: a new flow (sibling to `ReceiptCaptureFlow`, e.g. `ReceiptRetakeFlow`) drives capture → persist new file → `ReceiptScanProcessingScreen` (existing, `attemptFactory` pointed at the new file) → on success, opens `ReceiptConfirmSheet` in a new edit mode carrying `existingTransactionId`, the new `ReceiptParseResult`, and the new local file path. It does **not** call `ReceiptIngestService.ingestBytes` (that path is create-new-transaction only).
- **Commit**: `ReceiptConfirmSheet`'s Save action, in edit mode, calls a new `TransactionRepository.replaceArtifactAndReprocess(transactionId, newLocalFilePath, mimeType, parseResult)`: (a) loads the existing `outbox_artifacts` row for the transaction, (b) deletes its local file and issues a Storage delete for its `storage_path` (best-effort, see Edge Cases), (c) deletes that `outbox_artifacts` row, (d) inserts a fresh row (new id, new local path, `storagePath = null`) for the same `transactionId`, (e) writes the new OCR-derived fields onto `outbox_transactions` — the same field set `ingestReceipt` writes today (`merchantRaw`, `categoryGuess`, `categoryConfidence`, `ocrConfidence`, `ocrServiceConfidence`, `lineItemsConfidence`, `rawOcrText`, `parseFailureReason`, `amountMyr`/`needsAmount` unless the user overrides in the sheet) — leaving user-owned fields (`categoryUser`, `placeStatus`/place lock, `impactUser`) untouched, (f) replaces `outbox_line_items` for that transaction, (g) recomputes `pipelineStatus` via the existing `needsReview` predicate, (h) sets `syncStatus = 'pending'`.
- **Sync side**: `SyncWorker.run` needs **no changes** — it still finds exactly one `outbox_artifacts` row per transaction (the invariant the replace design was chosen to preserve), uploads it to a fresh `storage_path` keyed by the new artifact id, and upserts `transactions`/`receipt_artifacts` exactly as today.
- Two decisions that matter most: (1) one-current-artifact-per-transaction via replace, chosen specifically so `SyncWorker`'s existing `getSingleOrNull()` query keeps working unmodified; (2) retake results always land on the existing confirm sheet for explicit human confirmation rather than auto-applying, so a rescan can never silently overwrite a field the user previously corrected by hand.

## Decision Logic
- Local file exists at `localThumbnailPath` → show it directly (fastest, fully offline).
- Local file missing but `remoteStoragePath` set → resolve and show a signed URL; show `ReceiptThumbnail`'s existing loading-skeleton state while resolving.
- Both absent → show the existing static placeholder plus a short explanatory label; no tap-to-view affordance.
- `pipeline_status == 'needs_review'` (i.e. `ReceiptParseResult.lowConfidence`: `combinedConfidence < lowOcrConfidenceThreshold` (0.5), or amount used the keyword fallback, or `amountSuspicious`, all already computed at ingest in `receipt_parse_pipeline.dart`) → show the quality-nudge tag; otherwise show none.
- Retake completes successfully → always land on `ReceiptConfirmSheet` for explicit confirmation, regardless of the new pass's confidence — never auto-write fields.
- User cancels/backgrounds out before Save → discard the newly captured local file; zero writes to `outbox_artifacts`/`outbox_transactions`; original state fully preserved.
- Save pressed in edit mode → overwrite only OCR-derived fields with the new pass's values; fields the user already owns via manual correction (`categoryUser`, `placeStatus='user_locked'`, `impactUser`) are left alone by the reprocess step itself (still editable in the same sheet, same as initial capture).
- Old artifact's remote Storage delete fails or can't be attempted (offline, or the old object never finished syncing) → proceed with the local replace and transaction update regardless (never block retake on a delete succeeding); queue the remote delete for later best-effort cleanup rather than retrying synchronously inline.

## Edge Cases
- Retake attempted offline: the OCR/LLM call itself needs network (self-hosted `ocr-api`); on failure, the existing `ReceiptScanProcessingScreen` retry/failure UI already handles it, and on permanent failure the retake is abandoned with the original transaction/artifact completely untouched (no partial writes occur before explicit confirm).
- Retake confirmed seconds after the original capture, before `SyncWorker` has uploaded it yet: there is no remote `storage_path` to delete — skip the remote delete (nothing exists there yet), but still delete the local file and local `outbox_artifacts` row so the sync worker can't race and try to upload a file that's about to disappear.
- Retake confirmed while offline, old artifact already synced: local swap and transaction update happen immediately (offline-first); the remote delete of the old Storage object is deferred until connectivity returns — the superseded object may transiently persist in Storage but stays scoped to the owner via existing RLS, and gets cleaned up once online.
- Two retakes in quick succession: the confirm-sheet Save flow is synchronous/blocking per attempt, so a second retake can't start until the first's local replace has completed — no local race; worst case is two queued remote deletes for two different old paths, both harmless.
- Retake on a transaction that already has `place_status='user_locked'` (user manually confirmed a place earlier): the reprocess must not reset that lock — it's a user-owned field, not OCR-derived, and should survive exactly as today's `updateTransaction`/`updateTransactionPlace` already keep it isolated from OCR fields.
- Deleting the old artifact's local file fails (permission error, already gone): non-fatal — proceed with the DB-level replace regardless; the local file is disposable, the DB row is authoritative.
- Non-image share-ins (e.g. PDF, supported today via `file_picker` in `receipt_capture_menu.dart`): the zoom viewer is undefined for non-raster mime types. Assumption flagged for the implementer: this spec covers the common camera-capture case (JPEG/PNG/HEIC); a PDF should get a "open externally" affordance in the viewer rather than an attempted `InteractiveViewer` render, but the exact behavior needs explicit confirmation before building.
- Signed URL expires mid-view: acceptable — it's fetched once per screen-open for the current session; resuming the app later simply re-resolves a fresh URL on next load.
- **Existing receipts with no image reference**: audited, doesn't occur. `receipt_artifacts`/`outbox_artifacts` existed since the very first migration (`20260511000000_init.sql`) and `ingestReceipt()` has always written exactly one artifact row per transaction — there's no historical population of transactions lacking an artifact server-side, so **no backfill migration is required**. The only practical "no accessible image" state is a transaction whose local file is gone and whose Storage upload never completed (e.g. created fully offline, device reset before first sync) — already handled by the "both absent → placeholder + explanatory label" path above, a display-time fallback, not a data migration.

## Performance Considerations
- Local-file-first display is effectively free (no network) for the common case — consistent with the app's offline-first design.
- Signed URL resolution costs one Storage RPC per screen-open, only in the fallback (missing local file) case — not on the hot path for most users.
- `InteractiveViewer` over a single already-decoded image is cheap; no extra image processing beyond what the existing thumbnail rendering already does.
- Retake repeats the same OCR/LLM cost as an initial capture (one `services/ocr-api` call) — an existing cost incurred again, at explicit user request, not a new load pattern.
- Storage cost stays bounded under replace semantics — never more than one object per transaction, avoiding unbounded growth from repeated retakes.

## Security Considerations
- Signed URLs must be short-lived and never persisted to disk/logs — regenerated per view rather than cached, since the private `receipts` bucket exists specifically to scope receipt photos (which can show card-number tails, addresses, purchase detail) to their owner.
- Old-artifact remote delete is scoped by the existing owner-only RLS (`receipts_delete_own` on `storage.objects`, `ra_delete_own` on `receipt_artifacts`) — no new policy needed, same authenticated-session pattern already used in `sync_worker_flutter.dart`/`pending_imports_repository.dart`.
- No new abuse surface: retake reuses the exact same authenticated capture/OCR call path as a first capture. Assumption flagged: existing rate-limiting/abuse controls on that call path (if any) are assumed to already cover repeated invocation; this spec does not add new throttling, but retake makes the OCR call trivially repeatable by design, so it's worth the implementer confirming that's acceptable.

## Tradeoffs
- **Replace vs. version artifact history** (resolved with the user): versioning preserves a full audit trail of every scan attempt and never silently deletes a user's original photo, but requires changing `SyncWorker.run`'s artifact query off `getSingleOrNull()` (which throws once more than one row exists per transaction), plus a defined "which artifact is current" rule, plus unbounded storage growth. Replace was chosen — it costs the ability to look back at a bad original scan, but needs zero schema/RLS/`SyncWorker` changes and matches the product's "simple, consumer-friendly, not an accounting tool" framing.
- **Auto-apply new OCR results vs. always confirming**: auto-applying on high new-confidence saves one tap, but risks silently overwriting a field the user manually corrected earlier — undermining the existing `user_field_corrections`/learned-confidence investment. Always routing through the confirm sheet costs one extra tap but guarantees a rescan can never silently discard a prior correction.
- **New "enhanced image" pipeline vs. showing only the original**: a deskewed/enhanced variant could theoretically read better for faint thermal receipts, but `services/ocr-api`'s preprocessing is tuned for Tesseract accuracy, not human legibility, and persisting it would mean a second image artifact and a second sync path per transaction. Showing only the original keeps one artifact/one sync path and avoids showing users a machine-oriented image that may look worse to a human than their own photo.
- **Signed-URL fallback vs. local-file-only**: local-only is simpler (no Storage read-back path) but permanently strands any reinstalled/new-device user from ever verifying old receipts — directly undermining this feature's trust goal. The fallback costs one new repository method and one Storage RPC, only in that fallback case.

## Implementation Guidance
Suggested order of work:
1. `TransactionRepository.resolveDisplayImage(transactionId)` + `TransactionView.remoteStoragePath` (`transaction_repository_native.dart`/`_web.dart`, `transaction_view.dart`) — no UI yet; verify by manually deleting a transaction's local file and confirming signed-URL fallback resolves.
2. Fix `transaction_detail_screen.dart:233` to pass real `localPath`/`imageUrl` from step 1's resolver into `ReceiptThumbnail`. Independently shippable — fixes the dead UI slot with zero risk to write paths.
3. Build the full-screen viewer (`lib/features/tx_detail/receipt_image_viewer_screen.dart`), pattern-matched on `place_picker_screen.dart`'s fullscreen-route/overlay-bar structure; wire from the thumbnail's `onTap`.
4. Add the low-confidence nudge tag, driven off the `pipelineStatus`/confidence fields `_load()` already fetches — no new data plumbing.
5. Build `TransactionRepository.replaceArtifactAndReprocess(...)` with a focused Drift-layer unit test (insert transaction+artifact → call replace → assert exactly one artifact row remains with a new id/path, transaction fields updated, user-owned fields untouched).
6. Build the retake orchestration (capture → `ReceiptScanProcessingScreen` → `ReceiptConfirmSheet` edit mode) and add the edit-mode branch to `ReceiptConfirmSheet` (accepts `existingTransactionId`, calls `replaceArtifactAndReprocess` instead of `ingestReceipt` on save).
7. Wire the Retake entry point(s) (viewer's Retake button, at minimum) to the step-6 orchestration.

Inspect closely before touching: `lib/data/repositories/sync_worker_flutter.dart` (confirm its `getSingleOrNull()` assumption still holds — it's load-bearing for the replace design), `lib/data/local/tables.dart` `OutboxArtifacts` (no schema change expected, confirm), `lib/features/share/receipt_confirm_sheet.dart` (understand its current create-only assumptions before adding edit mode), `lib/widgets/receipt_card.dart` (confirm the photo is not accidentally wired into the carousel — its comment explicitly forbids that).

Risk to flag: the Storage delete of the old artifact has no atomic guarantee alongside the DB writes (separate DB update + separate Storage delete call) — treat it as best-effort/non-blocking per Edge Cases; its failure must never block the retake commit itself.

## Testing Strategy
- Repository unit test: `replaceArtifactAndReprocess` leaves exactly one `outbox_artifacts` row (new id/path), updates OCR-derived transaction fields, and leaves user-owned fields (`categoryUser`, `placeStatus='user_locked'`, `impactUser`) untouched.
- Repository unit test: `resolveDisplayImage` — local path when file exists; signed-URL fallback when local file missing but `storagePath` present; "unavailable" state when neither exists.
- Widget test: `transaction_detail_screen` renders a real image (not the placeholder) when `localThumbnailPath` is set — direct regression test for the exact dead-wiring bug found during this investigation.
- Widget test: nudge tag renders only when `pipelineStatus == 'needs_review'`.
- Integration test extending the existing `receipt_batch_e2e.dart` pattern: full retake from a seeded low-confidence transaction through confirm, asserting final DB state (one artifact, updated fields, `syncStatus='pending'`).
- Manual/functional acceptance: retake while offline (OCR call fails) leaves original untouched; retake then cancel before Save leaves original untouched; retake on a place-locked transaction preserves the lock.
- Performance validation: not applicable at meaningful scale (single-image, user-initiated actions) — just confirm the added signed-URL call doesn't visibly delay screen open in the common (local-file-present) case.

## Rollout Plan
- No database migration, so no cross-service ordering concern — this is a client-only feature reusing existing backend surface as-is.
- Ship the view-only pieces first (thumbnail wiring fix + full-screen viewer, Implementation Guidance steps 1-4) as a standalone release: purely additive and read-only, zero risk to existing save/sync paths, trivially revertible by rolling back the client build.
- Ship retake (steps 5-7) in a following release once the view-only piece is validated — it's the only part touching write paths (`outbox_artifacts`/`outbox_transactions` mutation, Storage delete).
- No feature flag strictly required (both pieces are additive UI/entry points, not changes to existing behavior); if staged exposure is preferred, gate only the Retake action behind a remote flag so it can be disabled instantly without pulling the view/verify functionality.
- Rollback: reverting the client release is sufficient at either stage since no server-side schema changes; a transaction that already had a confirmed retake keeps its new (post-replace) artifact even after a later app rollback — an accepted, permanent effect consistent with replace semantics.
