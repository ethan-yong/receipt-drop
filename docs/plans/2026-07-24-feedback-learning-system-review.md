# Architecture Review: Feedback Learning System

## Context

`docs/plans/2026-07-23-feedback-learning-system.md` (and its siblings, `2026-07-23-adaptive-ocr-strategy.md` and `2026-07-23-token-level-confidence-tracking.md`) describe three feedback-learning surfaces — merchant identity, per-user category preference, and global OCR misread-pattern detection — framed around confidence-weighted learning, recency bias, and conflict resolution.

This document is a senior-level architectural critique of what actually shipped against that framing, produced by directly reading the implementation (`merchant_extractor.dart`, `field_correction.dart`, `category_preference_repository.dart`, `category_preference_hint.dart`, `misread_pattern_extractor.dart`, `ocr_scoring.py`, `receipt_classifier.py`, the migrations under `supabase/migrations/202607230{10,20,30,40}000_*`, `enrich-transaction/index.ts`, `sync_worker_flutter.dart`, `receipt_parse_pipeline.dart`, `ocr_engine.py`) rather than the plan docs. The finding, consistent across all three surfaces: **the system is a fixed-constant tiered state machine, not a weighted-confidence-with-decay learning system.** Everything below is grounded in that gap, not the aspirational framing in the original spec.

This is a review document, not an implementation plan — its final section is a suggested order of operations for closing the gaps, which can be turned into an actual implementation task separately.

## 1. Executive Summary

All three learning surfaces are real, working code — not vaporware — and two related pieces (adaptive OCR strategy, token-level confidence) are further along than the original plan docs' framing suggests, already implemented behind default-off env flags with shadow-logging. But the core claims in `2026-07-23-feedback-learning-system.md` — confidence-weighted learning, recency bias, conflict resolution — are **not actually implemented as described** in any of the three surfaces:

- **Merchant alias confidence** is one of four hardcoded constants (0.9 / 0.75 / 0.2 / 0.88) selected by a 3-state gate (`user_locked` / agrees-with-established / corroboration count ≥ 3), not a computed `f(source_type, ocr_confidence, extraction_confidence)`.
- **Category preference confidence** is a single hardcoded constant (0.80), identical whether corroborated by 2 corrections or 200.
- **Recency decay exists nowhere.** `last_matched_at` and `last_corrected_at` are written on every update and read by nothing — dead columns for the one purpose the design claims they serve.
- **The misread-pattern learning loop is fully built and has zero consumers** — and the service that would consume it (`ocr-api`) has no Postgres client dependency at all. The v1 deferral is already recorded in `docs/system/decisions.md` (aggregation-only; names periodic export vs. proxy endpoint as options); what remains open is which of those architectures to pick, not whether the gap was noticed.

None of this makes the system broken — the fixed-tier approach is a legitimate, simpler design. The actual risk is that the system is described (in the plan docs and in how it'll likely be extended, e.g. LLM-prompt injection) as if it produces a meaningful continuous confidence signal, when it produces a label. Building more on top of that assumption (weighted blending into prompts, cross-surface confidence comparison) will silently inherit the gap.

## 2. Critical Issues (must fix before scaling)

**2.1 — Non-idempotent write-back in merchant alias correction (retry-driven double-counting).**
The serious defect is idempotency, not lost concurrent updates. `upsert_merchant_alias` increments `hit_count` with an atomic `hit_count + 1`, so concurrent callers do not drop counts. But `upsert_merchant_alias_from_correction` (called from `enrich-transaction/index.ts` on every enrichment, including retries and reprocessing) has no dedup guard keyed on `transaction_id`: any re-fire of the same logical correction re-increments `hit_count`, so a single correction can double-count toward the promotion threshold and prematurely promote a low-quality alias to `0.88` confidence. Separately, the established-lookup → candidate re-select → promotion path has a smaller TOCTOU (no `for update` between the second select and the confidence bump); that race's worst case is running the already-idempotent `set confidence = 0.88` twice — harmless. At scale, retry-driven double-counting silently corrupts the one dataset the whole merchant-learning surface depends on, with no error signal. (Bonus for 2.3: the write-back selects only `predicted_value`/`confirmed_value` from `user_field_corrections` and discards the correction's `confidence` column — the one continuous OCR-confidence signal available is never used as a weight.)

**2.2 — Corroboration gate is enforced client-side only, not at the data layer.**
`lookup_category_preference()` returns rows unconditionally, including `correction_count = 1` (uncorroborated) rows. The `>= 2` corroboration threshold is checked only in `receipt_parse_pipeline.dart` at the one current call site. Any future consumer of this RPC — a new client version, another service, a re-run of the backfill script, the planned LLM-prompt injection — that doesn't reimplement this exact threshold will leak single-source noise as validated user preference. This is a landmine baked into the schema/API contract, not a nice-to-have hardening.

**2.3 — "Confidence-weighted learning" is not real; it's a label, not a score.**
Across both merchant and category surfaces, "confidence" values are chosen from a small fixed set based on which branch of a state machine fired — never computed from OCR confidence, extraction confidence, or corroboration volume as the design claims. This matters specifically because the design's own "Intended Future Use" (LLM prompt injection, cross-surface comparison) assumes confidence is a continuous, comparable signal. It isn't. Anything built on top of it under that assumption will be quietly wrong.

**2.4 — No recency/time decay anywhere, despite being a headline design claim.**
`last_matched_at` (merchant) and `last_corrected_at` (category) are write-only. A merchant-alias correction from a year ago carries identical weight to one from this morning; a stale, corroborated-but-now-wrong category mapping never loses influence just because it's old. For a receipt app specifically — merchants rebrand, storefronts change tenants, users' own categorization intent shifts — this is a real correctness risk, not a theoretical one, and it's the cheapest of the critical gaps to close because the columns already exist.

**2.5 — Misread-pattern learning is dead infrastructure; consumption architecture is deferred, not undecided.**
The write/aggregate path (`misread_pattern_extractor.dart` → `upsert_misread_pattern` RPC → `ocr_misread_patterns` table) is genuinely well-built and its privacy guarantee (no raw values, single-char substitution pairs only) is real and verified end-to-end. But `lookup_misread_patterns()` has zero callers anywhere in the codebase, and `services/ocr-api` has no Postgres/Supabase client dependency at all in `pyproject.toml`. Closing this loop still requires choosing an architecture — narrow DB credential on `ocr-api` (breaks the documented "OCR API sits beside Supabase, not behind it" design) vs. edge-function proxy fetch-and-forward (latency + cache invalidation) vs. periodic export — but that deferral is **already recorded** in `docs/system/decisions.md` (rejected for v1; both candidate shapes named). What has not been made is the *choice among those options*. Continuing to accumulate pattern-write volume before picking one is still pure cost with no current ROI.

## 3. Important Improvements (next iteration)

- **3.1** Turn `last_matched_at`/`last_corrected_at` into functioning decay in the *read* path (`lookup_merchant_alias`, `lookup_category_preference`), e.g. exponential decay applied at query time. Highest ROI item on this list — the data already exists, only the read-side math is missing.
- **3.2** Add an idempotency guard to merchant alias write-back (dedup by `transaction_id`) so retries/reprocessing cannot re-increment `hit_count`; optionally wrap the candidate re-select + promotion bump in `for update` to close the minor TOCTOU in 2.1 (the bump itself is already idempotent).
- **3.3** Move the category-preference corroboration gate into `lookup_category_preference()` itself (filter `correction_count >= 2` in SQL) so the contract is safe for any future consumer, not just the current call site.
- **3.4** Either compute confidence for real (`weight = f(source_type, ocr_confidence, extraction_confidence)` as originally described) or stop calling the current fixed-tier approach "weighted" in docs — the mismatch between design language and implementation will mislead the next engineer (human or AI) who reads the plan docs and assumes the math exists.
- **3.5** Fix the `CategoryPreferenceRepository` naming/architecture split: it only reads (`lookup`); the actual write (`upsert_category_preference`) lives in `sync_worker_flutter.dart`, disconnected from the class whose name implies it owns both. Either fold the write in for cohesion, or rename the class to reflect read-only responsibility.
- **3.6** Handle the "LLM didn't run" gap in category preference lookup — it's currently keyed only on `ocr.understanding.merchantName` (the LLM's read) in `parseReceiptFile`, *before* `parseReceiptOcrText` runs. Heuristic merchant candidates from `merchant_extractor.dart` are **not** already available at that call site; they only exist after parsing completes. Closing the gap therefore requires a pipeline reorder (lookup after the heuristic pass, or a second best-effort lookup keyed on the top heuristic candidate), not "pass an already-computed fallback." This is a documented deliberate tradeoff in `docs/system/decisions.md` (non-regression vs. today's baseline when the LLM is absent), not an oversight — still worth closing if preference coverage matters when LLM is skipped.
- **3.7** Pick one of the two already-named misread-pattern consumption architectures in `docs/system/decisions.md` (periodic export vs. proxy endpoint / narrow DB credential) and record that *choice* before scaling write volume further. The v1 deferral itself is already written down; only the option decision remains open.

## 4. Design Gaps

- **No negative-signal handling anywhere.** Corrections only push toward a value; nothing decrements or invalidates a previously-promoted alias/preference once it's shown to be wrong again later. A user who corrects a merchant, then later corrects it back, has no mechanism to actively demote the bad alias faster than waiting for it to be statistically outcompeted.
- **No observability.** No logging/metrics on how often overrides fire, how often merchant-alias promotion happens, or why a given guess was made beyond re-deriving it by reading code. For a feedback-loop system, bad learned data is currently invisible until a user notices wrong output in the app.
- **No rollback/reset path.** If a bad alias or category mapping gets promoted (e.g. via the 2.1 retry-driven double-count), there's no admin or user-facing path to reset it short of direct DB intervention.
- **Merchant-alias ambiguity is stored but not obviously consumed.** Disagreeing corrections get a separate row rather than overwriting, which is the right instinct, but no UI/consumption path surfaces "this merchant is ambiguous" back to a user or moderator — it exists structurally and then goes nowhere.
- **Inconsistent sync-vs-server placement across the three surfaces, with no documented rationale.** Merchant-alias write-back is server-side (edge function); category-preference and misread-pattern write-back are both client-side (sync worker). This isn't necessarily wrong, but it's not an intentional, written-down split either — and it directly determines where idempotency/retry risk (2.1) and validation responsibility live.
- **Feedback-loop reinforcement risk is real, not hypothetical.** Because there's no decay and no negative signal, a systematic OCR misread of a chain's name (many users independently "correcting" to the same wrong alias) would hit the corroboration threshold and get promoted to `0.88` confidence with nothing to reverse it later. The design's "avoid overfitting to noise" goal is only partially met — corroboration count is a defense against a single bad actor, not against a shared systematic error source (e.g., a common OCR misread).

## 5. Suggested Next Iteration Plan

Ordered by leverage and dependency:

1. **Close the two correctness-critical gaps first**: idempotency on merchant alias write-back (dedup by `transaction_id` — 2.1/3.2), and move the category corroboration gate server-side into SQL (2.2/3.3). Both are data-integrity issues, not enhancements.
2. **Implement real recency decay in the read path** (3.1) — cheapest high-value fix since the underlying columns already exist; do this before anything downstream starts depending on "confidence" more heavily.
3. **Pick the misread-pattern consumption architecture** (2.5/3.7) among the options already named in `decisions.md` (periodic export vs. proxy / narrow credential) and record that *choice* — this unblocks or explicitly keeps deferred the misread-pattern consumption work, and should happen before more pattern-write volume accumulates.
4. **Resolve the confidence-modeling honesty gap** (2.3/3.4): either build the real weighted formula the docs describe, or rewrite the docs to describe the tiered state machine that actually exists. Pick one; don't let a third reader (or agent) inherit the mismatch again.
5. **Add minimal observability** (Design Gaps): a structured log or lightweight table recording override/promotion events, so learned-data quality is auditable without re-deriving it from raw tables.
6. **Only after 1–5, revisit the "Planned" LLM-prompt-injection work.** Injecting unweighted, non-decayed, unaudited "confidence" into prompts now would just propagate the same fragility one layer further downstream, and would be harder to unwind once prompts depend on it.
